## 1. 증상 (고객 보고 + 스크린샷)

- 절차: wizconfig 실행 → 컨트롤러 1 연결 → Device Search → IP 설정 후 Apply → Reset → (컨트롤러 2~4 추가를 반복). 10대를 넘기며 MAC 중복. 그동안 툴은 재실행하지 않았다. 문제가 생긴 뒤 다시 Search 해도 같은 증상.
- 스크린샷 1 (문제 상태, 상태줄 "Done: 17 devices found"): MAC `…07:18`, `…07:1A`, `…07:1D`, `…07:1F` 등이 두 번씩 나오고, 그중 하나는 이름 칸이 비어 있다. **8~17행이 주황색(= Phase 3 개별 조회가 아직 반영되지 않은 색)으로 남아 있다** [확인: 코드상 주황은 `_loading_color`, 개별 조회 응답이 처리돼야 검정으로 바뀐다].
- 스크린샷 3·4 (고객 측 설명 "툴을 껐다 켜고 재검색하면 괜찮아진다"): 17행이 서로 다른 MAC.
- 고객 회신 요지: "저희가 테스트용으로 만든 건 괜찮은데", "wiznet 껐다 켜고 나서 재검색하면 괜찮아진다".

### 4-2. 가설과 검증 방법

| ID | 가설 | 지지 | 반대·한계 | 검증 |
| --- | --- | --- | --- | --- |
| H1 | **MAC 표기 차이**(대소문자·공백·제어문자)로 키가 달라 병합을 통과 | F3, F6. 이름 빈 행 = 다른 경로의 부분 응답일 수 있음 | 펌웨어가 대문자로만 쓴다면 성립 안 함. **미확인** | 진단 로그로 `repr(bytes)` 확인(§6) |
| H2 | **툴 내부 상태 누적**(소켓·스레드·리스트)이 장치 수 증가와 함께 깨짐 | "재실행하면 정상", `96429c5` 의 의심, BUG-CONF-SOCK-PILEUP | 소켓 누적은 "응답 못 받음"을 만들지 "중복 행"을 직접 만든다는 근거는 없다 | `a200692` 포함 빌드로 같은 절차 재현 |
| H3 | Phase 1 응답이 **여러 출처 주소로 갈라져** 한 장치가 둘로 파싱 | per-addr 구조(#35) | F1·F2 때문에 병합에서 합쳐져야 함. H1 과 결합할 때만 성립 | 로그에서 같은 MAC 의 두 출처 주소 |
| H4 | **IP 변경·Reset 직후** 옛 IP/새 IP 에서 응답이 겹침 | 고객 절차가 IP 변경 반복 | 같은 MAC 이면 병합됨(F2). H1 과 결합해야 | 캡처(`pktmon`/Wireshark UDP 50001) |
| H5 | 같은 출처 주소로 답하는 장치끼리 합쳐짐 | `TASKS.md` 2026-09-07 실측 | **중복이 아니라 누락**을 만드는 방향 | — (이번 증상과 반대) |

### 4-3. "10대 이상"에 대해

- 코드에 10 이라는 한도·상수는 없다 [확인]. `max_parallel_sockets` 는 0(무제한)이고, 재시도 한도 기본값도 3~5다.
- 10대 부근에서 달라지는 것은 **Phase 3 동시 소켓·스레드 수**와 **누적 검색 횟수**뿐이다. 이 둘이 원인이라는 증거는 없다 [미확인].
- 8~17행(= 10행)이 주황으로 남은 것은 관찰이지만, 응답이 늦어서인지(진행 중 캡처) 반영이 안 된 것인지는 스크린샷만으로 가를 수 없다.
- **정직한 결론: 10대 이상에서만 생기는 이유는 아직 설명하지 못한다.**

## 5. 대응 설계 — "합치기" 전략

### 5-1. 처음 안(철회)과 새 안

| | 처음 안 | 새 안 |
| --- | --- | --- |
| 위치 | `WIZMSGHandler`(Phase 1 파싱 직후) | `_merge_search_results`·`get_search_result`·Phase 3 복원 루프에서 쓰는 **MAC 키 정규화 함수 하나** |
| 하는 일 | MAC 이 같은 행을 합침 | MAC 을 `strip().upper()` 로 정규화해 키로 쓴다. 표시값·원본 바이트는 그대로 둔다 |
| 문제 | F2 때문에 이미 되는 일을 반복. 키가 다르면 효과 없음 | H1 일 때만 효과. 아닐 때는 무해하지만 효과도 없다 |

### 5-2. 선택지별 장단점

| 선택지 | 장점 | 단점·위험 | 판단 |
| --- | --- | --- | --- |
| A. 정규화 키 + 진단 로그 (채택) | 변경 작음, 되돌리기 쉬움, 원인 신호를 남김, H1 이면 증상 해소 | H2~H4 이면 증상은 그대로 | **채택** |
| B. Phase 1 에서 같은 MAC 행 합치기 | 단순 | F2 로 이미 같은 일을 함 | 불채택 |
| C. 증상 가림(표시 단계에서 중복 행 숨기기) | 즉시 깔끔 | 원인 은폐, 평행 배열 어긋남 위험, 진짜 중복 장치도 숨김 | 불채택 |
| D. 로그만 먼저 받고 수정 보류 | 오판 위험 최소 | 고객이 기다림 | A 에 포함(진단 로그가 같은 목적) |

### 5-3. A 의 세부 결정

| 결정 | 선택 | 이유 |
| --- | --- | --- |
| 합칠 때 남길 값 | 기존 행 유지, **비어 있지 않은 값만 갱신**(현행 `_merge_search_results` 규칙 그대로) | `c96fb08` 이 이미 검증한 규칙 |
| 평행 배열 | 병합 함수 안에서만 수정, 5개 배열 길이 동일 유지 | `aaca66a` 의 교훈 |
| 진짜 중복 장치(MAC 복제) | 합치되 **경고 로그**(MAC·출처 주소·필드 수) | 숨기지 않고 흔적을 남김 |
| 진단 로그 | 병합 후 정규화 키가 겹치는데 원본 바이트가 다른 쌍을 `repr` 로 경고. 개수 변동·소켓 수도 한 줄 | H1~H4 판별용 |
| 로그 레벨 | 평소 정상(중복 없음)이면 아무것도 안 남김 | 잡음 방지 |

### 5-4. 예상 결과

- H1 이 원인이면 중복 행이 사라지고 로그에 원본 바이트 차이가 남는다.
- H1 이 아니면 중복은 그대로지만 로그에 **중복 쌍의 원본 바이트와 개수 변화**가 남아 H2~H4 를 가릴 수 있다. 이 경우 수정은 실패가 아니라 **관측 장치**로서 성공이다.

### 6-1. 고객에게 요청할 것
1. 새 exe 로 **같은 절차**(1~4번)를 반복하고, 중복이 생기면 **툴을 닫지 말고** 증상 화면을 캡처한다.
2. `%USERPROFILE%\.wizconfig\logs\wizconfig.log` 를 보낸다(로그 수준은 Option → Log Level → Debug).
3. 가능하면 Advanced Search Options 의 **Verbose Wire Log** 를 켜서 같은 절차를 한 번 더(원시 요청·응답 바이트가 `[WIRE]` 로 남는다).
4. 컨트롤러 개수, NIC 개수(Wi-Fi 포함), 몇 번째 장치를 추가할 때 처음 생겼는지.

### 6-2. 성공·실패 판정
- 성공: 같은 절차 17대 이상에서 중복 행 없음 + 로그에 정상 기록.
- 부분 성공: 중복은 남지만 로그에 원본 바이트·개수 변화가 있어 H1~H4 중 하나로 좁혀짐.
- 실패: 증상 그대로이고 로그에도 단서가 없음 → 패킷 캡처 요청, `a200692` 단독 효과 분리 시험.

## 7. 알려진 한계와 하지 않는 것

- 원인이 확정되기 전에는 "고쳤다"고 보고하지 않는다. 증상 가림(선택지 C)은 하지 않는다.
- 10대 이상 조건은 설명되지 않았다. 재현되지 않은 채로 효과를 약속하지 않는다.
- WIZ550·WIZ1x0SR 병합 경로는 이번 범위가 아니다(같은 키 함수를 쓰게 할지는 H1 확인 후 결정).
- 고객 버전은 1.6.2.3 이다. 현재 개발 트리(1.6.2.24-dev)와 차이가 커서, 새 빌드가 문제를 고치는지와 이 수정이 고치는지를 분리해 볼 필요가 있다(§6-2 실패 항목).
