# 터미널 다채널: 공존 규칙 · 안내 계층(SessionGuard) · HEX/ANSI 보기 설계

작성: 2026-10-21 · 짝 문서: [`DESIGN-terminal-multichannel-ko.md`](DESIGN-terminal-multichannel-ko.md)(본 설계) · [`ANALYSIS-netterm3-and-terminal-ko.md`](ANALYSIS-netterm3-and-terminal-ko.md)(근거)
상태: **설계만. 구현은 사용자 승인 전 금지.** 이 문서는 새 파일이며, 본 설계 문서는 결정 반영·단계 갱신만 했다.
갱신(2026-10-21 후속 3차): 사용자 승인 5건 반영 — D5 해제(P7 확정), D10 세션 상한 16, G8 = **압축 로테이트**(D20: 끝난 파일을 백그라운드 gzip, 압축 후 총량 상한, 보관 방식 `Stop`/`Rotate`, 세부는 사용자 확인 U1~U9), 같은 방향 연속 레코드 합치기(D21, 4 KiB/50 ms), 송신 깨우기 세션별 override 1차 제외. 측정 M22(F키 해결안 후보)·M23(gzip 비율). S1 선행 수정 5건의 착수 계획서는 [`PLAN-terminal-s1-ko.md`](PLAN-terminal-s1-ko.md).
갱신(2026-10-21 후속 2차): 4CH 담당자 시험 방식 답변 반영 — D8 확정, Mixed 채널(Client+Server 쌍), 세션 상한 16 권고, P5 문구 확정, 로그 용량 재계산(460800 baud·2일)과 분할·총량 상한 필수화, 송신 깨우기는 사용자 옵션(D19).
갱신(2026-10-21 후속): **D13~D18 확정 반영** — 송신 가능 상태표(§3.5), 보기 모드 배타(text/hex/ansi, D15), 영어 기본 문구 규약(§3.6, D16), 로그 안전장치(G6·G7, D18), 기존 결함 후보 3건과 F키 변형의 측정(M17~M20).
**문구 규약(D16)**: 이 문서의 한국어 사용자 문구·로그 문구는 **영어 문구를 쓰기 위한 명세(의미 정의)** 이다. 구현 때 영어로 확정하고 문구 사전 한 곳(§3.6)에 id → 문장으로 모은다. 기존 영어 라벨은 건드리지 않는다. 이미 영어로 확정된 문장(수신창 이벤트 줄 등)은 영어로 적었다.

## 0. 요약

1. **사용자 결정 반영**: D1(동시 연결·표시·송신 전부), D2(시리얼 포함), D3(탭↔그리드 토글)은 확정이다. 후속으로 D13~D18 도 같은 날 확정됐다(§6). 이에 따라 이 문서는 (A) 공존 규칙, (B) 경고 처리, (C) HEX/ANSI 보기, (D) 단계·시험 분리를 다룬다.
2. **먼저 알아야 할 새 사실 4건** (모두 측정, §1). 본 설계 초안의 가정 2개가 틀렸다.
   - 서버 세션 둘이 같은 포트를 열면 OS 가 막는다고 적었으나 **막지 않는다**. 둘 다 "listening" 이라 표시되고 접속은 첫째로만 간다(M1).
   - TCP Client+Server 동시 "불가" 규칙은 **불가가 아니라 경고 팝업**이다. 연결은 그대로 유지된다(M10).
   - 송신 깨우기(socketpair) 프로토타입은 지연 중앙값 25~30 ms → 0.3 ms, 4채널 편차 31~46 ms → 0.2 ms (M7). 당초 필수 격상을 권고했으나 **사용자 옵션 `Fast send wake`(기본 OFF)로 확정**됐다(D19). 측정은 TCP Client 핸들러만 했다.
   - 이 확장과 무관하게 **기존 결함 2건**이 보인다: 터미널이 열려 있으면 메인 창 F4/F5/F8 이 죽는다(M6), TCP Server 세션 수신이 약 64 KiB/s 로 묶인다(M8). 확장 전에 따로 고칠 것을 권한다.
   - 후속 측정으로 **기존 결함 후보 3건이 더 확인**됐다(M17~M19, 모두 [측정]): 자동 재접속 TCP Client 가 재접속 뒤 Send 를 침묵 무시하고 Disconnect 로도 못 멈춤 / 서버의 신규 접속 문의가 무한 대기하며 기존 클라이언트 송수신을 멈춤 / 재접속 켠 Connect 실패 시 버튼이 `Connecting...` 비활성에 갇힘. 셋 다 D13 의 송신 가능 상태 판정의 전제이므로 S4 전에 고친다. 또 D17(a) 를 구조 모사로 측정(M20)한 결과 메인 창 쪽 F4/F5/F8 은 복구되지만 터미널 창이 활성일 때는 여전히 불발이다.
3. **공존 규칙**은 50개로 정리했다(§3.2). 차단 11 · 경고 21 · 정보 16 · 조건부 2(G2 는 자동 이름이면 정보·사용자 지정이면 경고, G6 은 디스크 여유에 따라 정보·경고). D13 확정으로 S5~S7 이 정보·경고에서 차단으로 올랐고 S8·V7·G6~G8·L3 이 늘었다(42 → 48). D5 해제 승인으로 P7 은 정보(경고 없음)가 됐고, D20 압축 로테이트로 G9(삭제)·G10(압축 실패)이 늘었다(48 → 50). 개수는 §3.2 표를 스크립트로 센 값이다. 차단은 "측정 또는 읽음으로 실패가 확정된 것"에만 쓴다.
4. **HEX/ANSI**는 "변환은 표시 단계에서만, 원본 바이트는 세션이 링버퍼로 보관, 파일 로그는 항상 원본"을 원칙으로 한다(§4). NetTerm3 은 파일 로그가 보기 설정을 따라가고 ANSI 전환이 소급되지 않는다 — 우리는 의도적으로 다르게 한다. 보기 모드는 text / hex / ansi 중 세션별 하나만 고르며(D15) 동시 사용은 없다.
5. 구현은 Qt 무관 순수 모듈 3개(`session_guard.py`, `view_pipeline.py`, `raw_log.py`)로 분리해 자동 시험 대상으로 만든다(§5). 자동 시험은 규칙 50개에 147 케이스(+문구 사전 2, 깨우기 옵션 5), 보기 파이프라인·로그에 51 케이스(보기 36 + 압축 로테이트 10 + 합치기 5, §5.3). 실기기·사람 확인 20항목(H1~H20)은 따로 모았다(§5.4).
6. D13~D18 6개는 모두 **확정**(§6): 송신은 송신 가능 상태에서만(상태표 §3.5), 복사는 화면 기준 + 원본 복사 메뉴, 보기 모드는 text/hex/ansi 배타, 문구는 영어 기본(한국어는 명세), 매크로 F키는 터미널 창 한정, 로그는 HEX+ASCII 텍스트 기본. 복사 기본은 요청안(원본 기본)과 다르게 확정됐다 — 이유는 §4.6.

## 3. (B) 처리 방식

### 3.1 등급 기준

피로·오탐 방지 규칙(필수):

1. **차단은 [측정]/[읽음] 근거가 있는 규칙에만.** [추정]·[미확인]에 기대는 규칙은 최대 경고(P5, X1 의 시리얼 부분 등).
2. 같은 (규칙, 대상) 조합은 **연결 1회당 한 번**만 알린다. 사용자가 닫으면 세션 수명 동안 다시 안 띄운다.
3. 모달은 외부 영향이 있는 규칙(P3, X1, X2, S11, S12, G2 의 사용자 지정 경로)에만, "이 세션에서 다시 묻지 않기" 포함.
4. 헤더 배지는 세션당 최대 2개 + `+N`. 우선순위 차단 > 경고 > 정보. 4세션이 같은 규칙에 걸리면 한 줄로 합친다("CH1~CH4: …").
5. 정보는 로그에만 남기고 틱마다 반복하지 않는다(쓰로틀).
6. 규칙마다 사용 빈도를 로그로 세어 두고(세션 종료 시 `Guard stats`), 사용자 피드백 뒤 가지치기한다. 설정 파일 키로 정보·경고 규칙을 끌 수 있게만 하고 UI 는 만들지 않는다.
7. 색은 앱이 이미 쓰는 의미 색을 따른다 — 성공 `#5db872`, 경고 `#d4a017`, 오류 `#c64545`(`main_gui.py:4863-4872` 의 상태줄 색과 내부 디자인 가이드 시맨틱 색). 수신창 어두운 배경(`#1e1e1e`)에서의 가독성은 구현 때 눈으로 확인한다 [미확인].

### 3.5 송신 가능 상태표 (D13 확정)

**송신 가능**은 다음 네 상태뿐이다: **UDP bound / TCP Client 접속됨 / TCP Server 에 클라이언트 접속됨 / Serial 포트 열림.** 그 외 모든 상태(접속 시도 중, listen 만, 오픈 중, 실패, 끊김 + 재접속 대기)는 **불가**다. 표는 `protocol_tabs.py`·`comm_handlers.py` 를 읽고 만든 것이며 [읽음], 현행 동작 가운데 [측정]이 붙은 것은 스크래치 스크립트로 재현했다. "신규"는 D13 확정 후의 동작이다.

| # | 종류 | 상태 | 현행 동작 | 신규 | reason (툴팁·이벤트 줄) |
| --- | --- | --- | --- | --- | --- |
| 1 | UDP | 닫힘 / bind 실패 (`_handler` None) | Send 침묵 무시, TX 줄 없음 [읽음 `protocol_tabs.py:220-223`] | 불가 | `not open` |
| 2 | UDP | bind 중 (핸들러 생성~`bound` 전, 찰나) | 큐 적재 후 bound 뒤 전송, TX 줄은 즉시 [읽음 `comm_handlers.py:87-110`] | 불가 | `opening` |
| 3 | UDP | `bound` | `sendto`, 오류는 `Error:` 이벤트만 | **가능** (실패는 S8) | — |

적용 규칙:

1. **상태 판정은 핸들러 시그널에서 파생**한다. 탭의 `_connected`·`_handler` 플래그를 믿지 않는다(M17 이 그 불일치다). `SessionSpec.state` 는 §5.1 의 값 집합으로 갱신한다.
2. **불가 상태에서는 Send 버튼과 공용 송신의 해당 대상이 비활성 + 툴팁**(S1, S5). Enter·주기 전송·매크로처럼 버튼을 거치지 않는 경로는 데이터를 **폐기하고** 이벤트 줄 `Send: not sent — {reason} ({n} B discarded)` 만 남긴다(S5, S10). **TX 줄은 찍지 않는다.**
3. **TX 줄은 핸들러가 소켓·시리얼에 넘긴 뒤** 새 시그널 `sent(bytes)` 로만 기록한다. 넘기다 실패하면(전송 중 오류) 실패 이벤트(S8). 큐 누적은 없애므로 큐 상한이 필요 없다. 상태가 GUI 판정과 핸들러 사이에서 바뀌는 경주(race)를 위해 핸들러는 소켓이 없을 때 대기 중인 청크를 즉시 폐기하고 같은 실패 이벤트를 낸다.
4. **"연결되면 자동 송신"은 이번 범위에서 제외**한다(후속 후보). 사용자가 다시 보내야 한다는 점이 툴팁에 적힌다.
5. 이 표의 17행이 Guard 시험의 입력이다(S5~S7 의 상태 전수 시험).

### 3.6 문구 사전 규약 (D16 확정)

- 새 UI 문구는 **영어 기본**이다. 이 문서의 한국어 문구는 영어 문구를 쓰기 위한 명세이며, 구현 때 영어로 확정한다. 기존 영어 라벨(`Connection`, `Bind & Open` 등)은 건드리지 않는다.
- 문구는 **id → 문장 사전 한 곳**(제안: `terminal/ui_text.py`)에 모은다. `Verdict.text_id`·`log_text_id`·`recovery_id` 가 사전을 참조하고, 위젯은 문장을 직접 쓰지 않는다. id 형식은 `guard.<rule>.text` / `.log` / `.recovery`.
- 이벤트 줄·파일 로그의 문장은 기존 형식(`TCP Connected → …`)과 맞춰 영어로 고정한다. `Send: not sent — …` 처럼 이 문서가 이미 영어로 적은 것은 확정안이다.
- **번역 방식 선택(Qt Linguist `.ts` / 자체 사전 / gettext 등)은 미정**이다. 비교는 `s2egui` 가 따로 제시한다. 사전을 한 곳에 두면 어느 방식으로든 옮기기 쉽다.
- 자동 시험: 모든 id 가 사전에 존재하고, 문장의 `{placeholder}` 가 `params` 키와 일치하는지(2케이스, §5.3.1).

### 4.3 핵심 원칙

1. **P1 변환은 표시 단계에서만.** 핸들러 → 세션 경계의 `bytes` 는 절대 바뀌지 않는다. HEX·UTF-8·ANSI 는 모두 `ViewPipeline` 이 원본 레코드를 받아 표시 문자열을 만드는 순수 함수/클래스다.
2. **P2 원본은 세션이 보관한다.** 틱에서 비운 레코드를 **`RawHistory` 링버퍼**로 옮겨 상한까지 유지한다. 이것이 있어야 보기 전환·재렌더·원본 복사가 가능하다.
3. **P3 파일 로그는 보기와 무관하게 원본.** 핸들러에서 올라온 시점에 `RawLog` 가 기록(§4.7). NetTerm3 과 다른 점이다.
4. **P4 보기 설정은 세션별 + 전역 기본값.** 전역 기본값은 "새 세션의 초기값"이며 기존 세션을 바꾸지 않는다. 초기 기본은 `text`(UTF-8 해석 끔) / 너비 16.
5. **P5 `ansi` 모드에서는 배지가 항상 보인다**(V1). ANSI 가 소비한 바이트 수를 센다 — 무결성 시험에서 "왜 화면 글자 수와 RX 바이트가 다른가"를 설명하는 단서.
6. **P6 HEX 와 ANSI 는 공존하지 않는다(D15 확정).** 세션별 보기 모드는 `text`(기본) / `hex` / `ansi` 중 **하나만** 고른다. 하나를 켜면 나머지는 자동으로 꺼진다(라디오). "HEX 우선" 같은 우선순위 규칙과 그 배지는 두지 않는다. NetTerm3 은 ANSI+HEX 일 때 렌더 결과의 HEX 를 보여 주는데(분석 §1.8 a) 무결성 시험에 부적합하고, 공존을 막으면 "어느 바이트를 보여 주는가"의 모호함 자체가 사라진다.

### 4.4 보기 모드 (세션별, 하나만 선택 — D15)

보기 모드는 **상호 배타**다: `text`(기본) / `hex` / `ansi`. UI 는 세그먼트 버튼(라디오)이며 하나를 고르면 나머지는 자동으로 꺼진다. 전역 기본값은 새 세션의 초기 모드일 뿐 기존 세션을 바꾸지 않는다.

| 모드 | 하위 옵션 | 결과 | 비고 |
| --- | --- | --- | --- |
| `text` (기본, 현행) | `UTF-8 해석` 끔(기본) / 켬 | 끔: 0x20~0x7E 그대로, 나머지 `[HH]` — 현행과 동일(하위 호환). 켬: UTF-8 디코딩, 잘못된 바이트는 `[HH]`(대체문자로 바꾸지 않음 — 바이트 보존) | 한글 장치 출력 확인용. 현재 `_encoding` 자리가 이미 있음 |
| `hex` | 행 너비 8/16/32 | 오프셋 + HEX + ASCII 열(§4.8) | ¶ 토글 비활성 |
| `ansi` | — | ANSI 상태기계(색 제거 · 줄 내 커서) + UTF-8 디코딩(NetTerm3 와 같이 내장) + **줄 조립 필수**(§4.5) | 배지 필수(V1) |

- **모드 전환 = RawHistory 재렌더**(§4.6). RawHistory 의 상한을 넘겨 이미 버려진 오래된 내용은 **이전 모드로 그려진 채 화면에 남는다** — 구분선과 이벤트 한 줄로 알린다(V7).
- 없앤 것: "HEX+ANSI 동시 → HEX 우선" 규칙과 그 배지. 동시에 켤 수 없으므로 우선순위가 필요 없다.
- 시험: 모드 전이 3×2 = 6가지에서 다른 모드 플래그가 꺼지는지(MX1), 새 세션 초기 모드가 전역 기본값을 따르되 기존 세션은 안 바뀌는지(MX2), 경계 보존(RR3, RR4) — §5.3.2.

### 4.5 청크 경계 처리

| 대상 | 문제 | 규칙 |
| --- | --- | --- |
| `ascii` | 없음(바이트 단위, 상태 없음) | — |
| UTF-8 | 멀티바이트가 청크 사이에서 잘림 | 방향(RX)별 **증분 디코더** 1개. 잘린 꼬리는 보관하고 다음 RX 에서 완성. 새 RX 가 `idle_ms`(시작값 250) 동안 없으면 보관분을 `[HH]` 로 확정 표시. 다른 종류 레코드(TX·이벤트)가 끼면 즉시 `[HH]` 확정 후 그 레코드를 표시(순서 보존). 재렌더 시 디코더 상태는 초기화 |
| ANSI 시퀀스 | `ESC [ 3 1 m` 이 `ESC` / `[31m` 으로 갈림 | 상태기계가 청크를 넘어 유지(NetTerm3 와 동일). 미종결 시퀀스는 상한(시작값 64 B, OSC 는 256 B) 또는 유휴 `idle_ms` 후 **폐기하지 않고 `[HH]` 로 확정 표시** — 소비한 바이트를 조용히 지우지 않는다 |
| 줄 조립(`ansi` 모드에서만) | 커서 이동으로 현재 줄을 덮어쓰려면 "미완성 줄"이 필요 | `\n` 에서 방출, 512 B 상한, 유휴 120 ms 후 부분 줄을 방출(NetTerm3 와 같은 값 `:386-387`). **다른 종류 레코드(TX·이벤트)가 끼면 미완성 줄을 먼저 방출**해 TX/RX 순서를 보존(NetTerm3 은 120 ms 뒤 방출이라 TX 가 먼저 나올 수 있다 — `:485-503`) |
| HEX | 레코드 경계 | 레코드 단위로 새 헤더+새 행에서 시작(경계가 곧 정보). 같은 틱 안의 같은 방향 연속 레코드는 한 덩어리로 합쳐 표시(타임스탬프는 첫 레코드) |

결정성 요구: **같은 바이트열이 어떻게 쪼개져 들어와도 표시 결과가 같아야 한다**(유휴 확정이 개입하지 않는 한). 시험은 모든 분할점을 돌려 확인한다(§5.3 U5).

### 4.6 보존·복사·검색·상한

**RawHistory**

- 레코드 `(seq, kind, bytes, ts)`, 방향별 누적 오프셋 카운터 유지(HEX 오프셋과 무결성 대조용).
- 상한은 **바이트와 레코드 수 둘 다**: 시작값 256 KiB / 5,000 레코드 / 세션. 시리얼은 `ser.read(waiting)` 이 작은 청크로 쪼개질 수 있어(`comm_handlers.py:450-462`) 바이트 상한만 두면 레코드 오버헤드가 폭증한다 — 1 B 레코드는 약 130 B 를 쓴다(M14) → 5,000 레코드 최악 약 0.65 MB + 바이트 0.25 MB ≈ 0.9 MB/세션 → 16세션 약 14 MB [계산] (8세션이면 약 7 MB). 상한 초과 시 오래된 쪽부터 버리고 누적 카운터(`dropped_bytes`)를 올린다.
- 일시정지(⏸) 중에도 같은 상한이 적용된다(지금은 무제한, V5).

**재렌더**

- 모드 전환(`text` ↔ `hex` ↔ `ansi`, 상호 배타)은 RawHistory 를 화면 대기열로 되돌려 **기존 렌더 예산에 편승해 점진 렌더**한다. 한 번에 그리지 않는다 — 측정: 현행 변환 ≈ 0.7~0.8 ms/KiB, HEX ≈ 2.1~2.3 ms/KiB(M14) → 256 KiB 를 한 번에 그리면 ASCII 0.18 s, HEX 0.54 s 동안 UI 정지(오프스크린 값).
- 진행 중에는 헤더에 "보기 변환 중 {pct}%" 를 표시하고, 그 사이 새 데이터는 대기열 뒤에 붙는다. 변환 중 재토글은 이전 변환을 취소하고 다시 시작한다.
- **원본 보관 범위 밖(D15)**: RawHistory 상한에서 이미 버려진 오래된 레코드는 다시 그릴 수 없다. 재렌더는 RawHistory 가 가진 첫 레코드부터의 화면 블록만 갈아 끼우고, 그 앞의 블록은 **이전 모드 그대로 남긴다**. 경계는 구분선 한 줄 + 전환 이벤트 한 줄로 알린다(V7). 구현 후보: 화면 블록에 첫 레코드 `seq` 를 심어 두면 경계 블록을 찾을 수 있다 [추정, 미시험].
- ANSI 는 소급 가능하되 **RawHistory 시작점이 이스케이프 시퀀스 한가운데일 수 있다** — 시작점에서 상태 Normal 로 가정하고, 첫 줄이 깨질 수 있음을 알린다(정보 한 줄).
- 렌더 예산의 단위를 "바이트"에서 "비용 가중 바이트"로 바꾼다: `w_ascii = 1`, `w_hex ≈ 3`(M14 2.7~2.9 에 여유), `w_ansi` 는 구현 후 측정 [미확인].
- **4채널 합산 렌더 예산 검증(필수, M21)**: 예산·드롭 정책은 한 채널이 아니라 **4채널 합산 입력**으로 검증한다. 담당자 부하(채널당 44,000 B/s)에서 4채널 RX 만 171.9 KiB/s, 양방향이면 343.8 KiB/s 다. 렌더 0.8 ms/KiB(0.7~0.9, 오프스크린 상대값) 기준 UI 시간은 약 13.8%(12~15.5%) / 27.5%(24~31%)이고 `hex` 모드는 2.8배라 약 38% / 77% 가 되어 **HEX 에서는 드롭 정책이 실제로 작동할 수 있다** [계산]. 원칙 재확인: **표시는 버려도 파일 로그는 무손실**(핸들러에서 올라온 시점에 먼저 기록). 시험 RR5(`text` 모드 4채널 합산), RR6(`hex` 모드 4채널 합산): 틱당 처리량이 예산 이하이고, 드롭이 있으면 `dropped_bytes` + 화면 바이트 = 입력 바이트이며 파일 로그 바이트는 입력과 같다.

**max_lines 의 의미 바로잡기**: 지금은 틱 수(M9)이므로 HEX 로 바꾸면 한 블록이 수천 행이 될 수 있다. 화면 상한을 "표시 문자 수" 기준으로 바꿔야 한다(본 설계 S6a 에서 같이 처리).

**복사·저장 — 요청안과 다르게 확정(D14)**

- 요청 원칙은 "복사 기본도 원본 바이트 보존"이다. 그러나 **선택 영역 복사는 화면 글자 → 원본 바이트 역매핑이 없어서** 기본을 원본으로 만들 수 없다(레코드·행 매핑을 블록 데이터로 심으면 가능하지만 이번 범위에서는 과함).
- 확정(D14, 2026-10-21): `Copy (Selection)`·`Copy All`·`Save` 는 **현행 의미(화면 그대로)를 유지**하고, 메뉴에 다음을 **추가**한다: `Copy All as HEX`(RawHistory 전체), `Save Raw (.log, 파일 로그와 같은 형식)`. `ansi` 모드에서 화면 복사를 하면 알림 한 줄 "화면 기준 복사입니다(원본 아님)".
- 원본 보존이 필요한 쪽은 **파일 로그**가 책임진다(§4.7).

**검색**

- 화면 문서에서 `find`(현행). 필터 기능은 두 쪽 모두 없다 — 이번 범위에 넣지 않는다.
- HEX 모드에서는 HEX 열 문자열("48 65")과 ASCII 열을 검색할 수 있으나 행 경계를 가로지르는 바이트열은 못 찾는다 — 한계로 명시.
- 보기 전환 시 검색 위치는 초기화한다(문서가 새로 만들어지므로).

### 4.7 원본 파일 로그 형식 (D18 확정)

- 사람이 읽고 기계가 되돌릴 수 있는 한 줄 레코드:

  ```text
  # DESIGN raw-log v1  session=CH1 TCP Client 192.168.0.100:5000  started=2026-10-21 09:30:12
  09:30:12.345 RX 7 48656C6C6F0D0A  |Hello..|
  09:30:12.401 TX 4 41540D0A  |AT..|
  09:30:12.460 EVT TCP Connected -> 192.168.0.100:5000
  ```

- 필드: 시각(핸들러에서 올라온 순간), 방향, 길이, HEX(공백 없음), `|ASCII|`(참고용). **HEX 가 정본**이며 ASCII 열은 무시한다. 줄바꿈 바이트도 HEX 로 들어가 한 레코드 = 한 줄이 보장된다.
- 라운드트립 시험: 0x00~0xFF 모든 바이트와 임의 분할 → 기록 → 파싱 → 원본과 동일(§5.3 L).
- 용량 [계산]: 레코드당 HEX 2배 + ASCII 1배 + 머리 약 25 B → 대용량에서 원본의 약 3.2배. 921600 baud 한 채널(약 90 KiB/s)은 약 290 KiB/s ≈ 1 GB/시간 (4채널이면 약 4 GB/시간). 장시간 고속 시험을 위해 `.bin`(채널별 원본 스트림 + 시각 색인)을 옵션으로 둔다 — D18 확정(기본은 이 텍스트 형식).
- **안전장치(D18 확정 + 2026-10-21 필수 승인)**: (1) 로그 시작 시 남은 디스크 용량과 예상 용량을 안내한다(G6). (2) 크기 상한(시작값 1 GiB)에 도달하면 레코드 경계에서 새 파일로 분할한다(G7). (3) 끝난 파일은 백그라운드 스레드에서 gzip 으로 압축하고(D20), 총량 상한(세션별·전체, **압축 후 합계**)에 도달하면 보관 방식에 따라 로그를 멈추고 알리거나(`Stop`, G8) 가장 오래된 압축 파일부터 지운다(`Rotate`, G9). (4) 같은 파일명을 덮어쓰지 않는다 — 자동 이름은 접미사, 사용자 지정은 이어쓰기 또는 다른 이름(G2). (5) 쓰기 버퍼는 1초(시작값)마다 flush 해 비정상 종료 시 손실을 최대 약 1초로 제한한다 [제안].
- **용량 재계산 — 460800 baud, 최장 연속 약 2일(4CH 담당자 2026-10-21)** [계산, `log_capacity.py`; 측정 아님]. 8N1 이므로 46,080 B/s, 2일 = 172,800 s, 방향 하나 기준. 텍스트 형식의 레코드 길이는 `22 + 자릿수(N) + 3N` 이라 배율은 레코드 크기 N 에 따라 `3 + (22+자릿수)/N` 이다.

  | 조건 | 채널당 | 4채널 |
  | --- | --- | --- |
  | 원본 바이트 (= `.bin`, 색인은 1초 간격 2.6 MiB 로 무시 가능) | 7.42 GiB | 29.66 GiB |
  | 텍스트 HEX+ASCII, 레코드 125 B (배율 3.2, 라운드 기준값) | 23.7 GiB | 94.9 GiB |
  | 텍스트, 레코드 461 B (시리얼 핸들러 10 ms 주기 이론치, 배율 3.05) | 22.6 GiB | 90.6 GiB |
  | 텍스트, 레코드 64 B (배율 3.38) | 25.0 GiB | 100.1 GiB |
  | 텍스트, 레코드 16 B (배율 4.5) | 33.4 GiB | 133.5 GiB |
  | 텍스트, 레코드 1 B (배율 26 — 비현실적 최악) | 192.8 GiB | 771.2 GiB |
  | 양방향(TX+RX 모두 가득, 루프백) 텍스트 3.2 배 | 47.5 GiB | 189.8 GiB |
  | 양방향 `.bin` | 14.8 GiB | 59.3 GiB |

  - 쓰기 속도: 4채널 RX 만, 텍스트 3.2 배 ≈ 576 KiB/s ≈ 시간당 1.98 GiB (채널당 0.49 GiB/h). 디스크 쓰기 부담은 작고 **디스크 여유와 파일 관리가 문제**다.
  - 분할 파일 수(텍스트 3.2 배, 채널당 / 4채널): 256 MiB → 95 / 380개, 512 MiB → 47 / 190개, **1 GiB → 24 / 95개**, 2 GiB → 12 / 47개. 그래서 분할 상한 시작값을 256 MiB 에서 **1 GiB** 로 올렸다.
  - 배율은 레코드가 작을수록 커진다. **D21 승인(2026-10-21)**: 같은 방향의 연속 레코드를 최대 4 KiB / 50 ms 안에서 합쳐 한 줄로 쓴다 → 배율이 약 3.0 으로 안정된다. 규칙: 창은 첫 레코드에서 열리고 (a) 4 KiB 도달, (b) 첫 레코드로부터 50 ms 경과, (c) 방향 바뀜, (d) EVT 줄이 끼어듦, (e) 플러시·정지 중 하나면 닫는다. 타임스탬프는 첫 레코드, 바이트열은 그대로(라운드트립 불변). **시간 정밀도 영향 안내(옵션 도움말 명세)**: "Consecutive data in the same direction within 50 ms (up to 4 KiB) is written as one line, stamped with the time of its first byte. Timing inside that window and the boundaries between reads are not recorded. Turn this off to log every read separately (larger files)." 시각 오차는 최대 50 ms, 같은 방향 두 프레임이 50 ms 안에 오면 한 줄로 보인다. **끄는 옵션을 둔다**(`log.coalesce`, 기본 켬) — 프레임 간격·지연을 분석하는 시험(예: Modbus 프레임 간격)을 위해. 화면 표시(RawHistory)의 레코드 경계에는 영향이 없다(파일 로그만).
  - `.bin` 옵션 안내 문구(G6 경고 시, UI 영어 확정 전 명세): "At 460800 baud for 2 days, text logs need about 23.7 GiB per channel (about 95 GiB for 4 channels). The .bin format needs about 7.4 GiB per channel (about 29.7 GiB for 4 channels)."
  - **담당자 실측 부하(M21) 기준**(채널당 44,000 B/s, 방향 하나; 위 표의 46,080 B/s 는 이론 최대이고 실측은 그 약 95.5%): 12시간 4채널 RX 만 원본 7.08 GiB / 텍스트(3.2 배) 22.7 GiB, **양방향 원본 14.16 GiB / 텍스트 45.3 GiB**(채널당 RX 텍스트 5.7 GiB). 2일 4채널 RX 만 원본 28.3 GiB / 텍스트 90.6 GiB, 양방향 원본 56.6 GiB / 텍스트 181.3 GiB [계산, `log_capacity.py`]. 이 수치가 분할(G7)·총량 상한(G8)·시작 시 예상 용량 안내(G6)를 **필수**로 한 근거다.
  - **압축 로테이트 (D20; 사용자 원문 "압축 로테이트"를 `s2egui` 가 풀이한 것 — 세부는 사용자 확인 U1~U9)**:
    - 흐름: 기록 → G7 분할 → 끝난 파일을 압축 대기열에 넣음 → **백그라운드 스레드**가 `{file}.gz.tmp` 로 gzip(레벨 6, 1 MiB 청크) → 해제+CRC 로 검증 → `.gz` 로 이름 변경 → 원본 삭제. 기록 스레드와는 대기열만 공유한다(압축이 기록을 막지 않음, 시험 CP3). 압축 스레드는 하나이고 낮은 우선순위.
    - 실패·중단: 압축이 실패하거나(디스크 부족·쓰기 오류) 검증이 틀리거나 앱이 종료되면 `.gz.tmp` 를 지우고 **원본을 그대로 둔다**(G10). 다음 분할 때 다시 시도한다. 이전 실행이 남긴 `.log`/`.gz.tmp` 처리는 1차에서 `.gz.tmp` 삭제만 하고 나머지는 건드리지 않는다 [제안].
    - 총량: `.gz` 합계 + 압축 전 대기 파일 + 기록 중 파일. 상한은 세션별과 전체 둘 다. 도달 시 **보관 방식**: `Stop`(중단 + 알림, G8) 또는 `Rotate`(가장 오래된 `.gz` 부터 삭제, G9).
    - **삭제와 "자동 삭제 금지" 원칙의 충돌 판단 [제안, U1]**: 사용자 원문이 삭제를 포함하므로 기능은 둔다. 그러나 시험 증거(예: 2일 시험의 첫 몇 시간)를 말없이 지우는 것은 위험하므로 **기본은 `Stop`, `Rotate` 는 사용자가 켜야만** 동작하고, 켜면 로그 시작 안내(G6)에 삭제 규칙을 적고 삭제마다 이벤트 줄(G9)을 남기며, 삭제 대상은 이 실행에서 이 세션이 만든 검증 완료 `.gz` 로만 한정한다. 압축 자체는 삭제가 아니므로 기본 켬이다. 사용자가 "기본도 `Rotate`"를 원하면 기본값 한 줄만 바꾸면 된다.
    - 형식 [제안, U2]: gzip(`.log.gz`) — 표준 라이브러리만 쓰고 의존성 없음, 7-Zip·`gzip -dc`·Python 으로 풀린다. 단점: 메모장으로 바로 열 수 없다. zip/zstd 는 의존성 또는 단일 스트림 이점이 없어 제외.
    - `.bin` 옵션과의 관계 [제안, U5]: `.bin` 데이터 파일도 같은 방식으로 `.bin.gz` 로 압축한다. 시각 색인 파일(2일 약 2.6 MiB)은 평문으로 두고 같은 분할 번호의 데이터 파일과 한 쌍으로 지운다. 텍스트 로그에 이미 HEX 로 풀어 쓴 것은 압축이 잘 되고(전형 0.01~0.03), `.bin` 은 원본이라 이진 데이터면 압축이 덜 된다(무작위 최악 0.59 는 .bin 에서는 거의 1.0 에 가깝다 [추정])
    - **압축 중 디스크 일시 증가 [계산, U3]**: 채널당 최대 원본 1 GiB(분할 상한) + 압축본 최악 0.59 GiB = 1.59 GiB, 4채널이 동시에 겹치는 최악 6.4 GiB. 1 GiB 가 쌓이는 데 채널당 약 2.0 시간이 걸리고 압축은 1 GiB 당 8 s(텍스트)~61 s(무작위)라 겹치는 일은 드물다. 압축 전에 `남은 공간 < 원본 × 0.6` 이면 건너뛰고 G10.
    - 기본값 제안 [제안·미결정, U6]: 압축 켬 · 보관 방식 `Stop` · 세션별 총량 상한 8 GiB · 전체 32 GiB · 디스크 여유 예비 5 GiB(여유가 예비 아래면 압축 여부와 무관하게 G8). 이전 "디스크 여유의 80%" 시작값은 삭제를 쓰지 않을 때의 기준이라 대체한다.
    - **압축 후 용량 [계산 + M23 측정 비율]**: 2일 4채널 텍스트 94.9 GiB 가 압축 후 — 고정 반복 0.66 · 증가 카운터 1.33 · 텍스트 줄 2.09 · 이진 프레임 26.7 · 무작위 최악 55.8 GiB. 담당자 부하 12시간 4채널 양방향 텍스트 45.3 GiB 는 같은 비율로 1.0(텍스트 줄) ~ 12.7(이진 프레임) ~ 26.6(무작위) GiB. 비율은 합성 데이터라 실제 값은 H19.
    - 위 값들로 보면 전형적인 텍스트·패턴 데이터는 2일 4채널이 상한 32 GiB 안에 들어 삭제가 일어나지 않고, 무작위에 가까운 이진 데이터는 상한을 넘어 `Rotate` 면 앞부분이 지워지고 `Stop` 이면 중간에 멈춘다. 둘 중 무엇이 맞는지가 U1 이다.
- 보기 변환(HEX/ANSI/UTF-8)과 **완전히 독립**이다. 같은 세션을 ANSI 켠 채 로그해도 파일에는 원본이 남는다(V2).

### 4.8 HEX 화면 형식

```text
[12:00:01.123] RX 29 B   @0
00000000  48 65 6C 6C 6F 20 57 6F  72 6C 64 0D 0A 00 FF 41   |Hello World....A|
00000010  42 43 44 45 46                                      |BCDEF           |
[12:00:01.180] TX 4 B    @0
00000000  41 54 0D 0A                                         |AT..            |
```

- 헤더 줄: 현재 타임스탬프 모드(절대/경과/델타 — `receive_display.py:291-301`) + 방향 + 길이 + `@누적오프셋`(방향별, 0부터, `clear`·재연결에서 리셋).
- 한 행 16 B(옵션 8/16/32), 8 B 마다 간격 한 칸, 행 앞 오프셋은 **그 레코드 안의** 8자리 16진수, ASCII 열은 0x20~0x7E 외 `.`. 고정폭 글꼴(현재 Consolas)이 이미 쓰인다(`receive_display.py:189`).
- HTML 이스케이프 필요(`<` `&` 등). 색은 현행 RX/TX 색을 따른다.
- 현행 ¶(줄바꿈 raw) 토글은 HEX 에서 의미가 없으므로 비활성, ANSI 켠 상태에서도 개행을 해석하므로 비활성+툴팁.

### 4.9 기존 기능과의 충돌 점검표

| --- | --- | --- | --- |
| 비ASCII `[HH]` 표시 | HEX 에서는 모든 바이트가 HEX → 해당 없음 | `utf8` 에서 잘못된 바이트만 `[HH]` | `ascii` 모드는 현행 그대로 |

### 4.10 단축키

- HEX·ANSI·UTF-8 토글에는 **단축키를 새로 만들지 않는다**(툴바 버튼만). 충돌 가능성 0.
- 현재 선언된 키 [읽음, grep]: 메인 `F4 F5 F8 Ctrl+Q Ctrl+T`(`main_gui.py:757-782`), 터미널 `Ctrl+K Ctrl+Return Ctrl+↑/↓ Ctrl+F Ctrl+L Ctrl+= Ctrl++ Ctrl+-` 및 매크로 `F1~F12`. 본 설계 §6.5 의 신규 후보 `Ctrl+1..4`, `Ctrl+G`(뷰 전환)은 이 목록과 겹치지 않는다. 단 NetTerm3 에서 `Ctrl+T` 는 새 세션이지만 우리 앱에서는 터미널 열기이므로 **그 키는 쓰지 않는다**. 다른 다이얼로그(`fw_git_dialog.py` 등)의 단축키는 확인하지 않았다 [미확인].
- 현행 결함 M6(F4/F5/F8) 때문에 신규 단축키는 모두 `WidgetWithChildrenShortcut`/`WindowShortcut` 으로 선언한다.

### 4.11 NetTerm3 과 의도적으로 다른 점

| 항목 | NetTerm3 | 이 설계 | 이유 |
| --- | --- | --- | --- |
| ANSI 기본 | 켬 | 끔 | 무결성 시험 오도 방지 |
| ANSI+HEX 동시 | 가능(렌더 결과의 HEX) | **불가** — 보기 모드는 하나만(D15) | 무엇을 보여 주는지 모호해지는 것을 구조로 없앰 |
| ANSI 소급 | 안 됨 | RawHistory 로 가능(시작점 한계 명시) | 전환 후 이미 받은 것을 다시 볼 수 있어야 함 |
| 파일 로그 | 보기 따름·쓰기 오류 삼킴 | 원본·오류 알림(G4) | 시험 증거 |

### 4.12 한계 (ANSI)

NetTerm3 식 ANSI 는 **한 줄 안에서만** 커서를 움직인다. 다중 줄 화면 프로그램(vim·top 등)은 올바르게 보이지 않는다(`H`/`f` 는 열 0 으로만 이동, `AnsiLineRenderer.cs:139-142`). 목적은 셸 프롬프트 재그리기를 깔끔히 보는 것이다. 색 표시(SGR 매핑)는 이번 범위가 아니다(D15).

## 5. (D) SessionGuard 모듈 · 단계 · 시험

### 5.1 순수 모듈 3개

```python
# terminal/session_guard.py  (Qt 무관 — 자동 시험 대상)
class Level(Enum): BLOCK; WARN; INFO

@dataclass(frozen=True)
class SessionSpec:           # 세션의 읽기 전용 스냅샷
    key: str; kind: str      # 'udp' | 'tcp_client' | 'tcp_server' | 'serial'
    name: str; channel: int | None
    host: str; port: int; local_port: int; com: str
    state: str               # §3.5: 'idle'|'opening'|'connecting'|'reconnecting'|'bound'|'connected'|'listening'|'client_attached'|'prompting'|'failed'
    #                        # 핸들러 시그널에서 파생 (탭 플래그 아님, M17)
    log_path: str | None; macro_running: bool; periodic_on: bool

@dataclass(frozen=True)
class Verdict:
    rule: str; level: Level; related: tuple[str, ...]
    text_id: str; params: dict      # 문구는 사전(id → 영어 문장 한 곳, §3.6)에서 만든다 (D16)
    log_text_id: str; recovery_id: str

@dataclass(frozen=True)
class GuardContext:
    local_ips: frozenset; search_ports: frozenset = frozenset({52000, 5001, 6550})
    max_sessions: int = 16   # D10 승인. TCP C/S 정책 필드는 두지 않는다(D5 해제 — P7 은 항상 통과)
    now: float; last_apply: dict[str, float]; capabilities: set  # 예: 'tx_wake'

def check_open(spec, others, ctx) -> list[Verdict]            # P1~P6, P9, G1/G3 연동
def check_add(kind, sessions, ctx) -> list[Verdict]           # P8
def plan_send(targets, sessions, line_ends, ctx) -> SendPlan  # S1,S2,S4 — 가는 세션/건너뛴 세션/요약 문구
def send_state(spec) -> SendState                              # (sendable: bool, reason: str) — §3.5 17행
def check_single_send(spec, ctx) -> list[Verdict]             # S5~S8 (불가 이유 → 툴팁·이벤트 줄)
def resolve_macro_target(target, sessions, ctx) -> MacroPlan  # S9,S10
def check_close(spec, ctx) -> list[Verdict]                   # S11,S12
def check_external(event, sessions, ctx) -> list[Verdict]     # X1~X5 (event: 'apply'|'fw'|'search'|'disconnect')
def check_slot_key(key, ctx) -> list[Verdict]                 # X6
def check_log_path(path, others, fs, ctx) -> list[Verdict]    # G1~G7 (fs: 주입 가능한 파일시스템 어댑터; G6 디스크 안내, G7 분할)
def badges(spec, view, ctx) -> list[Badge]                    # L1,L2,V1,V2,V3,V5,V6,R1,R2
def restore_report(config, ports, ctx) -> list[Verdict]       # R1~R4

# terminal/view_pipeline.py — HEX/UTF-8/ANSI 변환 (Qt 무관)
class ViewPipeline:  __init__(mode: 'text'|'hex'|'ansi', utf8: bool=False, width: int=16)  # 모드는 배타 (D15)
                     feed(record) -> list[Span]; flush_idle(now); reset(); stats  # 상태: 디코더·ANSI·줄 조립

# terminal/raw_log.py — 원본 로그 형식
def format_record(ts, direction, data) -> str ; def parse_line(line) -> (ts, direction, bytes)
```

설계 규칙: 시계·파일시스템·COM 목록·로컬 IP 는 **인자로 주입**한다(전역 호출 금지) → 시험이 결정적이다. Qt 위젯은 `Verdict` 를 받아 그리기만 한다.

**송신 깨우기 — 사용자 옵션으로 확정(D19)**: 같은 조건에서 지연 중앙 25~30 ms → 0.3 ms, 편차 31~46 ms → 0.2 ms(M7)로 효과는 크고 구현도 작다(핸들러당 `socketpair` 한 쌍 + `select` 목록 1개 추가). 그러나 측정은 **TCP Client 핸들러만** 했고, 담당자가 4채널 동시 송신/수신 편차 시험을 해 본 적이 없어(4채널 동일 부하만 함) 필수로 올릴 근거가 약하다. 사용자 결정으로 **필수가 아니라 옵션, 기본 OFF(현행 50 ms 폴링)** 다. 설정 항목·키·ON 전환 조건·도움말 문구는 본 설계 §6.4 에 있고, 이 문서는 안내문(§3.4)의 문구 선택과 시험(§5.3 TW1~TW5)을 맡는다. 서버 핸들러는 M8 때문에 `select` 구조를 어차피 고치므로 옵션 코드는 그 변경과 같이 넣는다.

## 7. 한계와 미확인

- M6(F4/F5/F8)은 메인 창과 터미널 구조를 **모사한 측정**이다. 실제 앱을 띄워 확인한 것이 아니다. 해결 후에는 실제 앱에서 한 번 확인한다.
- M8 은 루프백 최대 속도 송신이다. 실장비는 느리므로 "항상 64 KiB/s 에 묶인다"가 아니라 "그 이상의 수신은 서버 세션이 따라가지 못한다"로 읽는다.
- M7 프로토타입은 TCP Client 핸들러만 바꿨다. UDP·서버 핸들러, Serial(10 ms 슬립이라 대상 아님)은 측정하지 않았다.
- HEX 비용(M14)은 오프스크린 렌더라 화면에 그리는 비용이 빠져 있다. 상대 비교로만 쓴다.
- NetTerm3 은 이번에도 **실행하지 않고 소스만** 읽었다.
- 규칙 문구의 이해도·경고 빈도는 사람이 써 봐야 알 수 있다(H10).
- 4CH 구조는 담당자 확인으로 **해결**됐다(독립 4채널, M16). 남은 것: 서버 모드 초과 접속 시 동작(H1), D8 의 LP/RP·Mixed 매핑, 4CH 시험 방식.
- M17~M19 는 오프스크린 Qt·루프백으로 재현했다. 실제 장치에서의 재접속 타이밍·서버 문의 대기의 체감은 [미확인]. 저장소 코드는 수정하지 않았다.
- M20 은 구조 모사다. Tool 창이 부모의 `WindowShortcut` 문맥을 공유하는 것이 원인으로 보이나 Qt 소스는 확인하지 않았다 [추정].
- M21 의 부하 수치는 담당자 실측이며 우리가 재현하지 않았다. 단위가 시험마다 섞여(B/s vs 프레임) E2S 열은 직접 비교하지 않는다. 렌더 비율은 오프스크린 상대값이라 실제 화면 그리기 비용이 빠져 있다(H8, H17 에서 실기기로 확인).
- 논블로킹 소켓의 `sendall` 부분 송신 동작(S8)은 [일반지식]이며 이 PC 에서 재지 않았다.
- M22 는 구조 모사다. (A) 의 창 동작 부작용(작업 표시줄·Alt+Tab·메인 창과 붙기)은 측정하지 않았다 [미확인, H13].
- M23 은 합성 샘플(5종)이다. 실제 장치 데이터의 압축 비율과 압축 중 UI 체감은 [미확인, H19]. `.bin` 의 압축률은 측정하지 않았고 [추정]이다.
