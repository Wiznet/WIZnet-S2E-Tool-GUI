## 질문 1 — 확인 GET 응답이 1,792B 를 넘으면 SV/RT 가 조용히 사라진다. 의도한 동작인가?

**근거**: 툴의 Apply 요청은 `SET… + 확인 GET(약 130개) + SV + RT` 순서다(`WIZMakeCMD.py:489-565`).
확인 GET 의 응답이 1,792B 를 넘으면 `SV` 토큰 **앞**에서 `segcp.c:486` 이 걸려 IGNORED 가 서고, `segcp_ret_handler`(`:286`)가 오류 플래그 때문에 저장·재부팅을 하지 않는다. 앞선 SET 은 RAM 에만 남는다.
그런데 응답에는 `MC` 가 정상으로 들어 있어, 툴은 `len(MC)==17` 으로 **성공**이라 알려 준다.

**재현(소스 기반 가짜 장치, 실기기 아님)**: 문자열 칸을 전부 최대(도메인 4개 127, PI/PP 63, 접속 데이터 12개 31, DH 19)로 채우면 확인 응답이 1,846B(담당자 수치 1,865B 와 근접) → SV/RT 가 버려지고 MC 는 있음. 기본값(910B)에서는 저장·재부팅 정상.
문자열 칸을 거의 다 최대로 채워야 닿는 극단 경우다.

**여쭙는 것**:
- (a) 이 동작(저장 안 됨 + 성공처럼 보임)은 의도입니까, 놓친 경로입니까?
- (b) 툴이 대응해야 한다면 어느 쪽이 맞습니까?
  1. SV/RT 를 확인 GET 과 **다른 요청**으로 보낸다(펌웨어 변경 불필요).
  2. SV/RT 를 확인 GET **앞**에 둔다 → `segcp.c:1071` 때문에 그 뒤 GET 이 전부 지워져 확인이 불가능해 보인다.
  3. 펌웨어에서 SV/RT 는 헤드룸 검사 대상에서 뺀다.

## 질문 2 — 응답 `memset` 이 버퍼 끝을 넘을 수 있습니까?

**근거**: `proc_SEGCP_udp` 는 응답 헤더(`MA`+MAC 10B, `PW`+값+CRLF)를 쓴 뒤 `trep` 를 그만큼 전진시켜 `proc_SEGCP(treq, trep, …)` 에 넘긴다(`src/segcp.c:2625-2638`).
`proc_SEGCP` 첫머리는 그 포인터부터 `memset(segcp_rep, 0, CONFIG_BUF_SIZE)` 를 한다(`:480`). 전역은 `gSEGCPREP[CONFIG_BUF_SIZE]`(`:171`).
그러면 지우는 구간이 `gSEGCPREP` 끝을 `14 + strlen(PW)` 바이트 넘는 것으로 읽힙니다(PW 가 공백 1칸이면 15B).

**여쭙는 것**: 맵 파일에서 `gSEGCPREP` 바로 뒤에 놓이는 변수가 무엇입니까? 의도된 구조라면 무시하셔도 됩니다.

## 질문 3 — 미구현 명령 응답 길이: 4B 입니까 5B 입니까?

**근거**: 이전 답변은 "빠진 명령은 `XX\r\n` 4B". 소스의 `default:` 는 `sprintf(trep, "%c", SEGCP_NULL)` 로 공백 1칸을 쓰므로 `XX ␠\r\n` 5B 로 읽힙니다(`segcp.c:1067`, `segcp.h:133`).
**여쭙는 것**: 실기기(또는 시리얼 로그)에서 본 응답이 어느 쪽입니까? 11~15개 × 1B 차이라 크지 않지만, 툴의 크기 모델에 쓰려고 합니다.
