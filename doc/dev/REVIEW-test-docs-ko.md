# 시험서 비평 (2026-10-20)

대상: `doc/TEST-SCENARIO-by-product-ko.md`(제품별 시험서, 730줄), `doc/TEST-PROCEDURE-since-v1.6.2.15-ko.md`(최근 변경 확인표, 357줄).
방식: 문서를 다시 읽고, 같은 날 읽은 4port 펌웨어 소스와 대조했다. 아래 "사실"은 문서·소스에서 확인한 것이고, "판단"은 내 의견이다.

## 1. 잘 된 점 (유지)
- 사실: 제품(P1~P11)·공통(C1~C13) 분리, 항목 ID, 결과 기호(P/F/N/B/K)가 일관된다. 항목 수와 §5 요약표 숫자가 일치한다(스크립트로 대조: C 13개 군, P 11개 군 전부 일치).
- 사실: F 보고 양식(캡처·로그·순서)과 안전 수칙(백업·원복·펌웨어 업로드 금지·⚠ 표시)이 있다.
- 사실: 담당자가 Python 없이 exe 만으로 따라 하게 쓰였다.

## 3. 구조적 약점

1. **두 문서가 같은 항목을 이중으로 갖는다.** R7(PROCEDURE)과 P8-19~24c(SCENARIO)가 사실상 같다. 한쪽을 고치면 다른 쪽이 낡는다. 판단: 하나의 정본(SCENARIO)에 두고 PROCEDURE 는 "변경 → 항목 ID" 색인만 남기는 편이 안전하다.
2. **기대값이 "코드·스펙을 읽은 추정"이다**(문서 머리말이 인정). 실기기 실행 전 기대가 틀릴 가능성이 있고, E2 가 그 예다. 판단: 항목마다 근거 등급 열(`소스 확인` / `스펙만` / `실측`)이 있으면 담당자가 기대를 얼마나 믿을지 알 수 있다.
3. **모호한 입력.** "임의의 값", "현재와 다른 값"이 5개 행에 있다(스크립트 검색, 행 번호는 미정리). 재현 불가·결과 비교 불가. 판단: 구체 값과 되돌릴 값을 적는다.
4. **사전 조건 열이 없다.** DHCP 서버, 시리얼 루프백, 같은 기종 10대, 구 FW 등 "없으면 못 하는 것"이 본문 속에 묻혀 있다. N(미시험)이 대량 발생할 구조다. 판단: 항목별 필요 조건 열을 두고 N 사유 코드를 받는다.
5. **우선순위·소요가 없다.** 총 213행(C 77 + P 136, 스크립트 집계)인데 최소 스모크 경로가 없다. 판단: 필수 20개 내외의 "스모크"와 "전체"를 구분한다.
6. **성공 판정이 사람 눈에 의존.** "오류 팝업이 없다", "빈 항목이 없다" 같은 부정형이 많다. 새로 생긴 **ⓘ 표시**(응답 끝 누락)는 C2 의 합격 기준에 아직 없다 — ⓘ 가 보이면 F 로 보고하라는 한 줄이 S2 에만 있다.
7. **S 분류(§6)와 본문이 연결되지 않는다.** C12(10대 이상)는 사실상 사람이 못 하는데 본문에 남아 있고, S6 이 같은 내용을 가리킨다. 판단: C12 에 "S6 으로 대체, 장치가 10대 있을 때만"을 명시한다.

## 4. 빠진 것
- 응답 끝 누락(ⓘ)·`[REPLY-INCOMPLETE]` 로그 확인 항목.
- "Apply 성공 팝업 + 저장 안 됨"(S1) — 성공 팝업만 보고 P 를 적지 않도록, 모든 Apply 항목은 **재검색 후 값 확인**이 합격 기준이어야 한다. C4 는 이미 그렇게 쓰였지만 P8 일부 항목(P8-22 "완료 팝업, 장치 정상 응답")은 팝업만 본다.
- 오류 입력 항목(포트 `65536` 등)이 C4-14/15 에 있으나 **기종별 문자열 길이 경계**(NP 9/10, PI/PP 63/64, 도메인 127/128, DH 19/20, SD 31/32)를 한 표로 모은 곳이 없다. 이 경계표는 `fw_4ch_string_field_limits` 메모리에서 만들 수 있다.

## 5. 제안 순서
1. E1~E4 정정(작다, 사용자 결정은 E1 하나).
2. 근거 등급 열과 사전 조건 열 추가(표 구조 변경 — 양이 많아 별도 승인).
3. PROCEDURE 를 색인으로 축소(구조 변경).
4. 경계표 신설.
5. 위 정정은 **다른 기종 FW 소스 정리(`doc/fw/FW-SOURCE-*.md`) 결과가 나온 뒤** 기종별 기대값 재대조와 함께 한다 — 지금 고치면 E2 같은 기대 오류를 다시 만든다.
