# 터미널 다채널(최대 4채널 동시) 확장 설계

작성: 2026-10-20 · 갱신: 2026-10-21 (사용자 결정 D1~D3 확정 반영, 후속 문서 연결) · 짝 문서: [`ANALYSIS-netterm3-and-terminal-ko.md`](ANALYSIS-netterm3-and-terminal-ko.md) (근거·측정), [`DESIGN-terminal-guard-hexansi-ko.md`](DESIGN-terminal-guard-hexansi-ko.md) (공존 규칙 · 경고 계층 · HEX/ANSI · 실측 M1~M16)
상태: **설계만. 구현은 사용자 승인 전 금지.** 문서 두 개 외 기존 파일은 건드리지 않는다.

**2026-10-21 갱신 요약**: 사용자가 D1(동시 연결·표시·송신 전부)·D2(시리얼 포함)·D3(탭↔그리드 토글)을 확정했다 → §11 에 확정 표시. 후속 측정으로 이 문서의 초안 서술 2곳이 틀린 것이 드러나 고쳤다(§5.1 서버 포트 중복, TCP C/S 규칙). 단계(§8)에는 선행 수정·Guard·HEX/ANSI 를 넣었다.

근거 표기: **[읽음]** 소스에서 확인 / **[측정]** 스크립트로 확인 / **[추정]** 추론 / **[미확인]** 확인 수단 없음. 줄 번호 근거는 짝 문서에 있고, 여기서는 `분석 §N` 으로 가리킨다.

## 0. 요약

1. 지금 터미널은 프로토콜 탭 4개(UDP · TCP Client · TCP Server · Serial)를 **하드코딩**해 쥐고 있어서 같은 종류 연결을 둘 이상 만들 수 없다. 4CH 시험(채널 4개 = TCP Client 4개 등)이 안 되는 직접 원인이다 (분석 §2.3 #1).
2. 그러나 각 탭(`BaseProtocolTab` 하위 클래스)은 이미 "연결 설정 + 수신창 + 송신창 + 핸들러" 가 완결된 **세션 위젯**이고 핸들러는 인스턴스별로 독립이다 (분석 §2.6). 그래서 설계의 중심은 **"탭 4개 고정" → "세션 목록(최대 N개)"** 으로 바꾸는 것이다. 새로 만드는 부분은 작다.
3. NetTerm3 도 같은 방식(세션 N개 + 탭/그리드)이다. 채널 개념은 없다 (분석 §1.5). 우리는 여기에 **채널 번호 라벨 + 여러 세션에 한 번에 송신(매크로 대상 지정)** 을 더한다.
4. UI 는 **기존 탭 화면을 기본값으로 두고 `탭 | 그리드` 토글을 추가**하는 안을 권고한다. 단일 채널 사용자는 아무것도 달라지지 않는다.
5. 먼저 막아야 할 위험은 측정으로 확인된 것들이다: 수신창 단축키가 둘 이상 보이면 **모두 죽음**(해법 확인됨), 수신창 무제한 적재(4채널이면 1~6초 정지 가능), 폴링 송신 지연(최대 약 64 ms, 4채널 간 편차 최대 약 32 ms), 터미널 시험 0건.
6. 단계는 S0~S7(S6 은 a~e 로 분할), 단계마다 사용자 확인 지점이 있고 전부 로컬 커밋이다 (push 없음). 확장과 별개인 **기존 결함 2건**(터미널이 열리면 F4/F5/F8 불발, TCP Server 수신 약 64 KiB/s)은 S1 앞에서 따로 고칠 것을 권한다.
7. 결정 항목은 §11 의 D1~D18. **D1(동시 연결·표시·송신 전부), D2(시리얼 포함), D3(탭↔그리드 토글)은 확정**(2026-10-21). 나머지 중 D5·D8 은 사유·의도를 아는 사람 확인이 필요하다.
8. 후속 측정으로 가정 2개를 정정했다: 서버 세션 둘이 같은 포트를 열면 OS 가 막지 **않는다**(둘 다 listening, 접속은 첫째로만), TCP C/S 동시 "불가" 규칙은 **경고 팝업일 뿐** 차단이 아니다. 송신 깨우기 프로토타입은 지연 25~30 ms → 0.3 ms, 4채널 편차 31~46 ms → 0.2 ms 라 **필수로 격상 권고**한다(§6.4).

## 2. 코드로 확인할 것 vs 사람이 정할 것

사용자 지시("코드가 확인할 것과 사람이 확인할 것을 구분")에 따른 구분이다.

### 2.1 코드·시험으로 확인할 수 있는 것 (결정 불필요, 구현 후 자동 검증)

| 항목 | 확인 수단 |
| --- | --- |
| 같은 종류 핸들러 여러 개가 서로 간섭하지 않는가 | 로컬 TCP 에코 서버 4개 + 세션 4개, 채널별 고유 페이로드로 교차 수신 없음 확인 (이미 TCP Client 4개 동시 송신은 [측정]됨 — 분석 §2.5(3)) |
| 단축키가 4개 보여도 포커스 쪽만 동작하는가 | 컨텍스트 변경 후 같은 측정 반복 (변경 전/후 대조는 [측정]됨) |
| 기존 4탭 화면이 그대로인가 | S1 의 특성화 시험(탭 순서·이름·기본값·단축키·매크로 저장 왕복) |
| 매크로 대상 분배 (active / all / select) | 가짜 세션 N개로 호출 기록 확인 |
| 설정 저장·복원 왕복, 구버전 JSON 읽기 | 파일 왕복 시험 |
| 장치 프로파일 → 세션 구성 매핑 | `tests/fake_segcp_device.py` 의 4CH 프로파일(`profile_from_spec`)로 규칙 시험 |
| 종료 시 스레드가 남지 않는가, 4채널 동시 종료 시간 | 시험에서 `wait` 시간 측정 |
| 수신창 상한·드롭 표시 동작 | 대량 주입 시험 (분석 §2.5(2) 방식) |

### 2.2 사람이 정하거나 확인해야 하는 것

| 항목 | 누가 |
| --- | --- |
| "동시 제어" 의 정확한 뜻 (연결만? 표시까지? 동시 송신까지?) | 사용자 (D1) |
| 4CH 담당자가 **실제로 어떻게 시험하는가** — 시리얼 쪽도 PC 에 4개 연결하나, 아니면 이더넷 4채널만 보나 | 4CH 담당자 → 사용자 (D2) |
| 화면 배치 선호 (탭/그리드/독립 창), 기본값 | 사용자 (D3, D4) |
| TCP Client/Server 동시 불가 규칙을 왜 뒀나 — 설계서에 규칙만 있고 사유가 없다 [미확인] | 터미널 최초 작성 의도를 아는 사람 (D5) |
| 장치가 TCP Client 모드일 때 툴이 listen 할 포트가 LP 인가 RP 인가 (분석 §2.7) | 4CH/FW 담당자 (D8) |
| 데이터 평면(채널 TCP 포트·UART)이 실제 4CH 에서 모드 조합별로 맞게 흐르는가 | **실기기**. 가짜 장치(`fake_segcp_device.py`)는 설정 평면(UDP 50001)만 흉내 내고 데이터 평면은 없다 [읽음] |
| 4CH 구조: 전달받은 배경은 "독립 4채널", 명세 주석(`specs/devices/W55RP20-S2E-4CH.yaml:3`)은 "RS-485 Modbus RTU 버스 1개를 TCP 서버 소켓 4개가 공유" — 어느 쪽인지 [미확인]. 답에 따라 D2(시리얼 쪽 의미)·채널 라벨·크로스 시험 서술이 달라진다 | 4CH 담당자 (가드 문서 H2) |
| 장치 서버 모드가 TCP 접속을 몇 개까지 받는가 (같은 채널에 클라이언트 세션 2개 규칙) [미확인] | FW 담당자 (가드 문서 H1) |
| 4채널 동시 고속 시 체감 성능·화면 가독성 | 실기기 + 사용자 눈 |
| 시험 기록을 파일로 남기는 형식(파일명·통합 로그) | 사용자 (D7) |

## 3. 핵심 설계

### 3.1 용어

| 용어 | 뜻 |
| --- | --- |
| **세션(Session)** | 터미널의 연결 하나. 지금의 `BaseProtocolTab` 인스턴스 하나와 같다 (프로토콜 + 수신창 + 송신창 + 핸들러) |
| **채널(Channel)** | **장치** 쪽 UART 채널 번호 CH1~CH4. 세션에 붙는 **선택적 라벨**(`session.channel = 1..4 \| None`) |

세션과 채널을 분리하는 이유: 한 채널을 이더넷 세션과 시리얼 세션 두 개로 볼 수도 있고(D2), 일반 장치(1채널)나 채널과 무관한 연결도 같은 터미널에서 쓰기 때문이다.

### 3.2 구조

```text
TerminalPanel (QWidget, Qt.Tool — 기존)
 ├─ 툴바: 전역 줄끝 · [＋ 세션▾] · [탭|그리드] · Export/Import · 📌 · ✕
 ├─ SessionManager                    ← 신규. 고정 4속성을 대체
 │    ├─ sessions: list[Session]      (생성 순서, 최대 MAX_SESSIONS)
 │    ├─ add(kind, **init) / remove(session)
 │    └─ 시그널: session_added · session_removed · state_changed(session)
 ├─ SessionContainer                  ← 신규. 같은 세션 위젯들을 두 방식으로 배치
 │    ├─ 탭 뷰  (QTabWidget — 기존 화면)
 │    └─ 그리드 뷰 (QGridLayout, 열 수 = ceil(sqrt(N)))
 ├─ SendBar (선택, S4)                ← 공용 송신: [입력] [대상 CH1 CH2 CH3 CH4 · All] [Send]
 └─ MacroPanel (공용 1개 — 기존)      ← 슬롯마다 target 필드만 추가

Session = BaseProtocolTab 하위 클래스(UDPTab · TCPClientTab · TCPServerTab · SerialTab) + 메타
          { key, name, channel, color }                 ← 얇은 메타만 추가
          각자 자기 ReceiveDisplay · SendWidget · 핸들러(QThread) 를 가진다 — 변경 없음
```

핵심은 `TerminalPanel` 이 4개 탭을 속성으로 쥐고 있는 방식(분석 §2.3 #1·#2)을 `SessionManager` 로 바꾸는 것이다. 세션 위젯과 핸들러 코드는 거의 그대로다.

### 3.3 NetTerm3 에서 가져올 것 / 가져오지 않을 것

| NetTerm3 요소 | 판단 | 이유 |
| --- | --- | --- |
| 세션 N개 + 탭/그리드 토글, 그리드 열 수 = ceil(sqrt(N)) | **가져온다** | 4채널 동시 표시의 검증된 형태 (분석 §1.4) |
| 세션 이름 변경(더블클릭), 헤더 상태 점, 헤더 드래그 순서 이동 | 가져온다 (순서 이동은 후순위) | 채널 식별 |
| 큐 상한 + 틱당 상한 + 드롭 카운트 + (배압) | **가져온다** (S6) | 4채널 부하 위험 (분석 §2.5(2)) |
| 수신 줄 조립 (`\n`, 120 ms 유휴, 512 B) | 가져온다 (S6, 옵션) | 채널 간 로그 비교 |
| 로그 실시간 파일 기록 | **가져온다** (S6 앞당기기 가능) | G3 |
| Save/Load Setup JSON | 가져온다 (S6) | 시험 환경 재현 |
| 시리얼 흐름제어 4종 / 시리얼 자동 재연결 | 가져온다 (S6, D12) | 4CH 채널별 흐름제어 시험 |
| HEX 전체 보기 | 가져온다 (S6, 옵션) | 바이너리 시험 |
| 명령줄 세션 생성 (`--tcp-client` 등) | 가져오지 않는다 | 이 앱은 GUI 가 주, 요구 없음 |
| **ANSI 해석 기본 켬** | **가져오지 않는다 (켜더라도 기본 끔)** | 켜면 수신 바이트가 변형되어 무결성 시험에 부적합 (분석 §1.8 a) |
| 채널 개념 없음 | **우리가 더한다** | 채널 번호 라벨 + 대상 지정 송신 |
| 시험 코드 없음 | **우리가 더한다** | §9 |

### 3.4 세션 모델 (제안 인터페이스)

```python
# terminal/session_manager.py (신규, 제안)
MAX_SESSIONS = 8            # 이더넷 4 + 시리얼 4 (D2·D10 에서 확정)

class SessionMeta:          # 위젯에 붙는 얇은 메타
    key: str                # "s1", "s2" … 설정 파일에서 대상 지정용, 이름이 바뀌어도 불변
    name: str               # 사용자 편집 가능. 기본 "TCP Client 1" / 장치 연동 시 "CH1 :5000"
    channel: int | None     # 1~4 또는 None
    color: str              # 채널 구분 색 (탭/그리드 헤더 표시)

class SessionManager(QObject):
    session_added = pyqtSignal(object)
    session_removed = pyqtSignal(object)
    state_changed = pyqtSignal(object, bool)      # session, connected
    def add(self, kind: str, **init) -> BaseProtocolTab: ...
    def remove(self, session) -> None: ...        # 핸들러 stop → wait 후 위젯 폐기
    def connected(self) -> list: ...
    def shutdown(self) -> None: ...               # 전 세션 stop() 먼저 일괄 → 그 다음 wait (병렬)
```

`BaseProtocolTab` 에 추가할 것은 `meta`, `snapshot()` / `restore(dict)` (설정 저장용), `set_compact(bool)` (그리드용) 정도다. 연결·송수신 코드는 건드리지 않는다.

## 4. UI 안 비교

### 4.1 대안

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 탭만** (바깥 탭 CH1..CH4, 안쪽에 현재의 프로토콜 탭) | 현재 구조 위에 한 겹 더 | 기존 화면과 가장 가깝다 | 한 번에 한 채널만 보인다. 동시 *표시* 불가. 탭이 2겹이라 복잡 |
| **B. 그리드만** | 항상 2×2 | 한눈에 4채널 | 1채널 사용자도 좁은 칸을 본다. 현재 폭(480)에 안 들어간다 (분석 §2.3 #9) |
| **C. 탭 ↔ 그리드 토글 (권고)** | 세션 N개를 `탭 | 그리드` 로 전환. 기본은 탭 | NetTerm3 와 같은 검증된 형태. 단일 채널은 변화 없음. 같은 세션 위젯을 재배치만 하므로 구현 단순 | 그리드에서는 칸이 좁아 연결 설정 행을 접어야 한다 (`set_compact`) |
| **D. 별도 창 분리** | 채널마다 독립 창 | 멀티 모니터 | 창 관리 부담, 매크로·송신바 공용화가 어렵다. 이번엔 과함 |

권고: **C**. 이유: (a) G4 를 가장 잘 지킨다 (기본 화면 불변), (b) G1·G2 를 모두 충족, (c) 세션 위젯 재사용으로 새 코드가 적다.

## 5. 채널별 모델

### 5.1 연결

- 세션 추가: `[＋ 세션▾]` 메뉴 — UDP / TCP Client / TCP Server / Serial / **프리셋**(§5.6).
- 세션당 연결 설정·상태 표시는 지금 탭의 `Connection` 그룹 그대로.
- 같은 프로토콜 복수 허용. **서버 세션 둘이 같은 포트를 열면 OS 가 막지 않는다** — 둘 다 `listening` 으로 표시되고 접속은 먼저 연 쪽으로만 간다 [측정, 가드 문서 M1]. 핸들러가 `SO_REUSEADDR` 를 설정하기 때문이며(`comm_handlers.py:272`), 이 PC 에서 그 옵션을 빼도 직후 재listen 이 성공했다(M1c). 대책은 (1) `SessionGuard` P1 이 앱 안 중복을 막고 (2) 핸들러에서 `SO_REUSEADDR` 를 제거해 외부 프로세스 충돌(M1b)도 bind 오류로 드러나게 하는 것이다. UDP 같은 로컬 포트는 OS 가 10048 로 막는다(M2).
- **TCP Client + Server 동시 규칙 (`terminal_panel.py:214-222`)**: 이 규칙은 "불가"가 아니라 **둘 다 연결된 뒤 경고 팝업을 띄울 뿐**이다. 연결은 끊기지도 막히지도 않는다 [읽음, M10]. 4CH 는 채널마다 모드가 달라(예: CH1 서버 모드 ↔ 툴 클라이언트, CH2 클라이언트 모드 ↔ 툴 서버) 동시 사용이 정상 시나리오다. 규칙 해제는 팝업이 사라지는 것 하나뿐이다 (D5). 원래 사유는 여전히 [미확인].
- 모든 공존 규칙(차단/경고/정보 42개)과 문구는 가드 문서 §2~§3.
- 세션 수 상한 `MAX_SESSIONS` (권고 8).

### 5.2 송신

- 세션별 `SendWidget` 은 그대로 (Escape 해석, 줄끝, 주기 전송, 이력).
- **공용 송신바**(S4): 한 입력을 선택한 세션들로 동시에 보낸다. 대상: 채널 체크박스 + `All connected`. 줄끝은 세션별 설정을 따르되 "공용 줄끝 우선" 옵션 (현재의 `Per Tab` 콤보와 같은 개념, `terminal_panel.py:140-146`).
- 송신 직후 각 세션 수신창에 TX 로 기록 (`append_tx`, 현재 `_dispatch_send` 와 동일, `terminal_panel.py:209-212`). 단 현재는 **큐에 넣은 시점**에 TX 가 찍히고, 서버 세션에 클라이언트가 없거나 클라이언트 세션이 접속 전이어도 큐에 남았다가 나중에 전달된다 [측정, M4·M5]. 미연결 세션에 보내면 아무 표시 없이 무시된다 [읽음, M5b]. 송신 전 요약("CH1, CH3 → 2/4 연결")과 이 동작의 정리는 가드 문서 §3 (S1~S7, D13).

### 5.3 수신·표시

- 세션별 `ReceiveDisplay` 유지. 변경은 부하 보호뿐 (S6):
  - 대기 상한(`max_pending_bytes`)과 틱당 렌더 예산. 넘치면 **오래된 것을 버리고 `⚠ N B 생략` 한 줄을 표시**한다. 이때 파일 로그(§5.4)는 **수신 시점에 먼저 기록**되어 손실이 없다.
  - 렌더 타이머: 지금은 수신창마다 50 ms `QTimer` (`receive_display.py:112-115`). 세션 N개면 N개의 타이머가 각자 깬다. **공용 타이머 하나가 라운드로빈으로 세션당 예산만큼 렌더**하는 구조가 UI 정지를 막는다. 수치(예산 크기)는 시작값일 뿐 실측으로 조정해야 한다 — 분석 §2.5(2): 0.7~0.9 ms/KiB (오프스크린 기준이라 실제 화면에서는 더 느릴 것으로 본다 [추정]).
- 옵션: 줄 조립, HEX 전체 보기 (NetTerm3 방식). 기본은 현재 표시(ASCII + 비ASCII `[HH]`)를 유지한다.
- ANSI 해석은 **넣더라도 기본 끔**. 상세 설계(원본 링버퍼 `RawHistory`, 청크 경계, HEX 형식, 배지, 비용 가중 예산)는 가드 문서 §4.
- 수치 보정: HEX 덤프 렌더는 현행 변환의 약 2.7~2.9배 비용이라 예산에 가중치가 필요하다 (M14). `max_lines=2000` 은 줄이 아니라 **틱 수**다 — `appendHtml` 한 번이 `<br>` 이 몇 개든 블록 1개 (M9). S6a 에서 표시 문자 수 기준으로 바로잡는다.

### 5.4 로그

| 항목 | 설계 |
| --- | --- |
| 화면 로그 | 지금처럼 `QPlainTextEdit` + `max_lines` (2000). 변경 없음 |
| 파일 로그 | 세션별 `Log to file` 체크 → 수신/송신 바이트를 **핸들러에서 올라온 시점에** 줄 단위로 기록, 파일명 기본 `{장치 또는 세션이름}_{CHn}_{yyyymmdd_HHMMSS}.log`. **보기 설정(HEX·ANSI·UTF-8)과 무관한 원본 기록**(HEX 정본 + 참고용 ASCII 열, 라운드트립 시험)이며 NetTerm3 은 보기 문자열을 기록해 다르다 — 형식·용량·충돌 규칙은 가드 문서 §4.7·G 계열 (D18) |
| 통합 타임라인 (D7) | 선택. 한 파일에 `[시각] CH1 RX …` 처럼 채널 접두어를 붙여 모든 세션을 시간순으로 기록. 채널 간 순서 비교(교차오염·지연 분석)에 쓴다 |
| 시각 | 현재는 `time.time()`(수신창에 쌓는 시점, `receive_display.py:212-218`). 파일 로그는 **소켓 수신 직후의 시각**이 더 정확하다. 단 핸들러 루프가 50 ms 폴링이라 시각 정밀도는 약 50 ms 가 한계 (분석 §2.5(3)) [읽음 + 추론] |

### 5.5 매크로

현재: 공용 패널 1개, 슬롯 최대 12, F1~F12 `ApplicationShortcut` (`macro_panel.py:21-22,303-307`), 실행은 `MacroRunner` 스레드가 `send_requested(bytes)` 를 내보내고 `TerminalPanel` 이 **현재 탭**으로 보낸다 (`terminal_panel.py:201-212`).

변경:

1. **패널은 1개로 유지한다.** 둘이면 F 키가 모호해져 죽는다 [측정].
2. 슬롯 데이터에 `target` 추가:

   ```json
   {"name": "init", "rows": [["AT\\r\\n", 100]],
    "target": {"mode": "select", "sessions": ["s1", "s3"]}}
   ```

   `mode`: `active`(기본 = 현재 동작) · `all`(연결된 전부) · `select`(세션 key 목록). `target` 이 없는 구버전 JSON 은 `active` 로 읽는다 → **기존 저장값과 호환** (`set_all_data`, `macro_panel.py:413`).
3. `send_requested(bytes)` → `send_requested(bytes, target)`. 해석은 `TerminalPanel` 이 한다: 대상 세션 목록 → 각 `session.send_bytes(data)` (= 현재의 `handler.send` + `display.append_tx`).
4. 러너 스레드 → GUI 스레드로는 지금처럼 큐드 시그널을 쓴다. 여러 대상에 보내는 루프는 GUI 스레드에서 연속 호출(핸들러 `send` 는 deque 추가라 스레드 안전·즉시 반환) [읽음].
5. 대상이 연결 안 됨 / 사라짐: 그 대상은 건너뛰고 해당 세션 수신창에 이벤트 한 줄(`Macro: not connected, skipped`). 매크로 전체는 중단하지 않는다.
6. 행(row)마다 대상을 다르게 하는 안(`CH1: AT`, 지연, `CH2: AT`)은 더 유연하지만 표(Message/Delay)를 3열로 바꿔야 한다. 이번엔 슬롯 단위만, 행 단위는 후속 후보 (D6).

"동시" 송신의 한계: 핸들러가 50 ms 폴링이라 대상들에 닿는 시각이 어긋난다 — 루프백 측정에서 **4채널 편차 중앙 31 ms, 최대 32 ms**(핸들러 시작 시각이 제각각일 때), 맞추면 0.2 ms [측정]. 후속 프로토타입 2회 반복에서는 편차 중앙 31.2~46.5 ms(최대 48), 깨우기 적용 시 0.2 ms(최대 0.3) [측정, M7]. D1 확정(동시 송신 포함)에 따라 **§6.4 의 깨우기 개선을 필수로 격상 권고**한다. 개선 전에는 사용자 안내문(가드 문서 §3.4 하단)에 오차를 명시한다.

### 5.6 장치 연동 (4CH 자동 구성)

현재 "Open in Terminal" 은 장치 프로파일의 **채널 0 키**(`OP LP BR DB PR SB LI`)만 써서 탭 4개를 채운다 (분석 §2.3 #5). 4CH 는 채널 0~3 이 각자 값을 갖는다: 채널 0 은 레거시 코드, 채널 1~3 은 `channel_field_map.CH_FIELD_MAP` (`channel_field_map.py:31-57`)의 코드 (`AO/TO/JO` 동작 모드, `QL/GL/CL` 로컬 포트, `QH/GH/CH` 원격 IP, `AP/TP/JP` 원격 포트, `EB/WB/YB` 보레이트 …).

제안: 순수 함수 하나를 신설한다 (Qt 무관 → 시험하기 쉽다).

```python
# terminal/device_endpoints.py (신규, 제안)
def endpoints_from_profile(profile: dict, spec) -> list[ChannelEndpoint]:
    """장치 프로파일 + spec(channels 수) → 채널별 {channel, op_mode, ip, local_port,
    remote_ip, remote_port, baud, databit, parity, stopbit, flow}"""
```

세션 구성 규칙(제안 — **D8 에서 4CH 담당자 확인 필요** [미확인 부분 표시]):

| 장치 채널 동작(OP) | 툴 세션 | 주소/포트 | 비고 |
| --- | --- | --- | --- |
| 0 TCP Client | **TCP Server** (리슨) | 포트 = 장치 채널의 **원격 포트** | 현재 코드는 로컬 포트(LP)를 넣는다 (분석 §2.7) **[미확인]** |
| 1 TCP Server | **TCP Client** | 장치 IP : 채널 **로컬 포트** | 현재 코드와 같은 방향 |
| 2 Mixed | TCP Client (장치 서버 쪽) | 장치 IP : 로컬 포트 | 현재는 서버 탭으로 보냄(분석 §2.7) **[미확인]** |
| 3 UDP | UDP | 원격 = 장치 IP : 로컬 포트, 툴 로컬 포트 = 장치의 원격 포트 | UDP 방향성 문서 `research/2026-04-27-udp-remote-local-port-explained.md` 참고 후보 (읽지 않음) |
| 4~6 (SSL/MQTT) | — | — | 4CH 에서 숨김. 무시 |

시리얼 쪽: 채널별 UART 파라미터(보레이트·데이터·패리티·정지·흐름)로 Serial 세션의 설정을 채울 수 있다. **COM 포트 번호는 PC 에서 장치의 어느 UART 와 이어졌는지 알 수 없으므로 자동 선택 불가** → 사용자가 고른다 (사람이 확인).

프리셋(메뉴): `4CH 이더넷` (TCP Client 4개를 CH1~4 로 라벨) / `4CH 이더넷+시리얼` (D2 결과에 따라) / `Classic` (현재의 4탭).

## 6. 스레드·이벤트 구조

### 6.1 현행 유지 + 변경점

```text
   [ 세션 1 ]        [ 세션 2 ]  …  [ 세션 N ]               각 세션 = 독립
 핸들러(QThread)   핸들러(QThread)   핸들러(QThread)         select 폴링 루프 (변경 없음, §6.4 선택)
   │ data_received    │                 │                    스레드 → GUI: 시그널(큐드)
   ▼                  ▼                 ▼
 ReceiveDisplay    ReceiveDisplay   ReceiveDisplay           deque 적재 (상한 추가, S6)
   └────────────┬────────────┴───────────┘
        공용 렌더 타이머(S6)  ──▶ 세션당 예산만큼 렌더
 MacroRunner(QThread) ──send_requested(bytes, target)──▶ TerminalPanel(GUI) ──▶ 대상 세션들의 send()
```

- 핸들러는 변경하지 않는다. 스레드 수 = 세션 수(최대 8) + 매크로 러너 1 — 문제 되는 규모는 아니다 [추정].
- 새 스레드는 만들지 않는다.

### 6.2 수명 규칙 (전례: 커밋 `658f2f8` QThread GC 크래시)

1. 핸들러의 소유자는 세션이다. 세션이 폐기되기 전에 `stop()` → `wait()` 로 스레드를 끝낸 뒤에만 참조를 놓는다.
2. `SessionManager.remove()` 와 `shutdown()` 은 **먼저 모든 핸들러에 `stop()` 을 일괄 호출한 다음** 한꺼번에 `wait()` 한다 (현재는 탭별 순차 `wait(2000)`, 분석 §2.3 #8). 4채널 종료 지연이 2초×4 → 약 2초로 줄어든다 [추정].
3. 핸들러 시그널의 람다 연결(`lambda e: self.display...`, `protocol_tabs.py:302,386,474,617`)이 세션 폐기 후 호출되지 않도록 폐기 시 `disconnect` 한다 (시험으로 확인).

### 6.3 UI 스레드 예산

분석 §2.5(2) 측정에 따라 수신창 렌더는 양에 비례(≈0.8 ms/KiB)하고 상한이 없다. 공용 타이머가 틱마다 세션당 렌더 바이트 예산을 두고(시작값 예: 세션당 8 KiB ≈ 7 ms), 못 그린 분은 다음 틱으로 넘기며, 대기량이 상한(예: 세션당 1 MiB)을 넘으면 오래된 쪽을 버리고 표시한다. **수치는 시작값이며 실기기 4채널 고속 시험으로 조정한다** (사람 확인).

### 6.4 송신 깨우기 (**필수로 격상 권고**, S4 와 함께)

격상 근거(2026-10-21 프로토타입, 저장소 미수정, 2회 반복): 4채널 동시 송신에서 기존은 지연 중앙 24.9~29.6 ms(최대 63)·편차 중앙 31.2~46.5 ms(최대 48), `socketpair` 깨우기는 지연 중앙 0.3 ms(최대 0.6)·편차 중앙 0.2 ms(최대 0.3) [측정, M7]. TCP Client 핸들러만 바꿔 측정했고 UDP·Server 핸들러는 미측정이다. 서버 핸들러는 별도 결함(수신이 `select([srv], 0.05)` 한 번당 `recv(4096)` 1회라 약 64 KiB/s 에 묶임 — M8)이 있어 `select` 구조를 어차피 고쳐야 하므로 같은 변경에 묶는다.

아래는 최초 설계(변경 없음):

핸들러 루프는 송신 큐를 비운 뒤 `select(..., 0.05)` 에서 잔다 (`comm_handlers.py:100-112,184-197`). 그 사이 들어온 송신은 최대 50 ms 대기한다 — 루프백 측정: `send()`→수신 중앙 25~29 ms, p90 56 ms, 최대 약 64 ms [측정]. 개선안:

- TCP/UDP: 핸들러마다 `socket.socketpair()` 한 쌍을 두고 `select` 목록에 읽기 쪽을 넣는다. `send()` 가 큐에 넣고 쓰기 쪽에 1바이트를 쓰면 즉시 깨어난다. Windows 에서 `socketpair` 는 Python 3.5+ 에서 제공 [일반지식, 이 PC 에서 미실행].
- Serial: 루프가 `msleep(10)` 이라 지연 ≤ 10 ms (`comm_handlers.py:464`) [읽음]. 필요 없다.

이 개선이 없으면 "동시 송신" 은 수십 ms 어긋난다 (D1 에 따라 허용 여부 결정).

| R6 | TCP C/S 규칙 해제가 숨은 사유와 충돌 | 낮음/중 [사유 미확인] | D5 에서 사유를 먼저 찾고 해제 |

| R10 | 데이터 평면이 가짜 장치로 검증 안 된다 | 확정/중 | 실기기 게이트(S4·S5), 데이터 평면 가짜 엔드포인트 제안 |

| R12 | 설계서(`plans/terminal-utility-design.md`)와 코드가 이미 어긋나 있다 (분석 §2.1) | 확정/낮음 | 구현 후 설계서 갱신 항목으로 기록 |
| R13 | 서버 세션 둘이 같은 포트를 열어도 둘 다 "listening" — 한쪽은 죽어 있는데 정상으로 보인다 | **측정됨** (M1, M1b) | Guard P1 + `SO_REUSEADDR` 제거(M1c). 제거 후 재listen·실사용 회귀는 시험으로 확인 |
| R14 | TCP Server 세션 수신이 약 64 KiB/s 로 묶여 고속 채널에서 병목·상대 배압 (기존 결함) | **측정됨** (M8) | S1 선행 수정. 921600 baud 실기기 확인(H8) |
| R15 | 터미널이 열려 있으면 메인 F4/F5/F8 이 죽는다 (기존 결함) | **측정됨, 구조 모사** (M6) | S1 선행 수정(D17), 실제 앱에서 재확인 |
| R16 | TX 가 큐 삽입 시점에 찍혀 "보냈다"고 오해, 서버 세션은 옛 데이터가 나중에 전달됨 | **측정됨** (M4·M5) | D13, Guard S5~S7 |
| R17 | 보기 변환(ANSI)이 무결성 시험을 오도 | 중/높음 | 원본 링버퍼·원본 로그·배지 필수·HEX 는 원본 우선 (가드 문서 §4) |
| R18 | 경고가 너무 많아 무시됨(피로) | 중/중 | 등급 기준·1회 규칙·배지 상한 (가드 문서 §3.1), 사용 후 가지치기 |
| R19 | 4CH 구조 서술 불일치(독립 채널 vs RS-485 공유, M16) | 미정 | 담당자 확인(H2) 전에는 D2·크로스 시험 서술을 가정으로 표시 |
| R20 | 원본 파일 로그 용량(고속 4채널 약 4 GB/시간 [계산]) | 중/중 | D18 에서 `.bin` 옵션, 로그 시작 시 예상 용량 안내 |
