# 터미널 다채널(최대 4채널 동시) 확장 설계

작성: 2026-10-20 · 갱신: 2026-10-21 (사용자 결정 D1~D3, 후속 D13~D18 확정 반영, 후속 문서 연결) · 짝 문서: [`ANALYSIS-netterm3-and-terminal-ko.md`](ANALYSIS-netterm3-and-terminal-ko.md) (근거·측정), [`DESIGN-terminal-guard-hexansi-ko.md`](DESIGN-terminal-guard-hexansi-ko.md) (공존 규칙 · 경고 계층 · HEX/ANSI · 실측 M1~M20)
상태: **설계만. 구현은 사용자 승인 전 금지.** 문서 두 개 외 기존 파일은 건드리지 않는다.

**2026-10-21 후속 갱신 요약**: 사용자가 D13~D18 을 확정했다 — D13 송신은 송신 가능 상태(UDP bound / TCP Client 접속됨 / TCP Server 클라이언트 접속됨 / Serial 열림)에서만, 그 외는 폐기 + 이벤트 줄, TX 줄은 `sent(bytes)` 로만, 큐 누적 제거(가드 문서 §3.5 상태표) · D14 복사는 화면 그대로 + 원본 복사 메뉴 · D15 HEX 와 ANSI 는 공존 불가(보기 모드 text/hex/ansi 중 하나) · D16 새 UI 문구는 영어 기본(한국어는 명세, 문구 사전 한 곳) · D17 매크로 F키는 터미널 창 활성 시에만 · D18 파일 로그는 HEX+ASCII 텍스트 기본, 디스크 안내·분할·덮어쓰기 금지. 4CH 담당자 확인(독립 4채널, 서버 모드 접속 1개, NetTerm3 TCP C/S 동시 가능)을 반영해 남은 [미확인]을 정리했다. 후속 측정으로 **기존 결함 후보 3건**(M17~M19)과 D17 변형 측정(M20)이 추가됐다.

**2026-10-21 갱신 요약**: 사용자가 D1(동시 연결·표시·송신 전부)·D2(시리얼 포함)·D3(탭↔그리드 토글)을 확정했다 → §11 에 확정 표시. 후속 측정으로 이 문서의 초안 서술 2곳이 틀린 것이 드러나 고쳤다(§5.1 서버 포트 중복, TCP C/S 규칙). 단계(§8)에는 선행 수정·Guard·HEX/ANSI 를 넣었다.

근거 표기: **[읽음]** 소스에서 확인 / **[측정]** 스크립트로 확인 / **[추정]** 추론 / **[미확인]** 확인 수단 없음. 줄 번호 근거는 짝 문서에 있고, 여기서는 `분석 §N` 으로 가리킨다.

## 0. 요약

1. 지금 터미널은 프로토콜 탭 4개(UDP · TCP Client · TCP Server · Serial)를 **하드코딩**해 쥐고 있어서 같은 종류 연결을 둘 이상 만들 수 없다. 4CH 시험(채널 4개 = TCP Client 4개 등)이 안 되는 직접 원인이다 (분석 §2.3 #1).
2. 그러나 각 탭(`BaseProtocolTab` 하위 클래스)은 이미 "연결 설정 + 수신창 + 송신창 + 핸들러" 가 완결된 **세션 위젯**이고 핸들러는 인스턴스별로 독립이다 (분석 §2.6). 그래서 설계의 중심은 **"탭 4개 고정" → "세션 목록(최대 N개)"** 으로 바꾸는 것이다. 새로 만드는 부분은 작다.
3. NetTerm3 도 같은 방식(세션 N개 + 탭/그리드)이다. 채널 개념은 없다 (분석 §1.5). 우리는 여기에 **채널 번호 라벨 + 여러 세션에 한 번에 송신(매크로 대상 지정)** 을 더한다.
4. UI 는 **기존 탭 화면을 기본값으로 두고 `탭 | 그리드` 토글을 추가**하는 안을 권고한다. 단일 채널 사용자는 아무것도 달라지지 않는다.
5. 먼저 막아야 할 위험은 측정으로 확인된 것들이다: 수신창 단축키가 둘 이상 보이면 **모두 죽음**(해법 확인됨), 수신창 무제한 적재(4채널이면 1~6초 정지 가능), 폴링 송신 지연(최대 약 64 ms, 4채널 간 편차 최대 약 32 ms), 터미널 시험 0건.
6. 단계는 S0~S7(S6 은 a~e 로 분할), 단계마다 사용자 확인 지점이 있고 전부 로컬 커밋이다 (push 없음). 확장과 별개인 **기존 결함 2건**(터미널이 열리면 F4/F5/F8 불발, TCP Server 수신 약 64 KiB/s)은 S1 앞에서 따로 고칠 것을 권한다.
7. 결정 항목은 §11 의 D1~D18. **D1~D3(2026-10-21 오전)과 D13~D18(같은 날 후속)이 확정**, D4~D12 는 미결이다. D5 는 해제 근거가 확보됐고(NetTerm3 은 TCP Client/Server 동시 가능, 담당자 확인) 사용자 결정만 남았다. D8 은 4CH 담당자 확인이 필요하다.
8. 후속 측정으로 가정 2개를 정정했다: 서버 세션 둘이 같은 포트를 열면 OS 가 막지 **않는다**(둘 다 listening, 접속은 첫째로만), TCP C/S 동시 "불가" 규칙은 **경고 팝업일 뿐** 차단이 아니다. 송신 깨우기 프로토타입은 지연 25~30 ms → 0.3 ms, 4채널 편차 31~46 ms → 0.2 ms 이나 TCP Client 만 측정했고 담당자가 4채널 동시 송신 편차 시험을 해 본 적이 없어, **필수가 아니라 사용자 옵션 `Fast send wake`(기본 OFF)로 설계한다**(D19, §6.4).
9. **4CH 담당자 시험 방식 답변(2026-10-21) 반영**: D8 확정(장치 TCP Client 모드 → 툴 서버는 장치 원격 포트 RP 로 listen, UDP 는 툴 로컬 = 장치 원격 / 툴 원격 = 장치 로컬, 현 `fill_from_device` 의 LP 사용은 틀림 → TASKS `TODO-TERM-OPEN-IN-TERMINAL-PORT`). Mixed 는 장치가 서버로 시작해 클라이언트 접속 전 시리얼 데이터가 들어오면 클라이언트로 전환 → **한 채널에 툴 Client+Server 세션이 둘 다 필요**할 수 있어 D5 해제가 필수 근거가 되고 같은 채널의 쌍은 경고 금지다. 세션 수는 4채널 × (TCP Client + TCP Server + Serial) = 12 라 상한 8 은 부족 → **16 권고**(D10, 사용자 결정 대기). 서버 모드 두 번째 접속은 장치가 거부(P5 는 경고 유지). 시리얼은 터미널 = 간단 확인용이고 정식 무결성은 담당자의 자체 Python 루프백 프로그램이라 내장 무결성 자동검증은 범위 밖이다. 로그는 최장 약 2일·460800 baud 라 용량을 재계산했고(텍스트 채널당 약 23.7 GiB, 4채널 약 94.9 GiB, `.bin` 4채널 약 29.7 GiB) 분할·총량 상한·시작 시 예상 용량 안내는 **필수**로 승인됐다(D18, 가드 §4.7). 담당자의 4채널 동시 양방향 460800 부하 시험(최장 12시간, 채널당 약 44,000 B/s, 담당자 실측)도 반영했다: 12시간 양방향 4채널 로그는 원본 약 14.2 GiB·텍스트 약 45 GiB, 수신창 렌더는 4채널 RX 만으로 UI 시간 약 14%(양방향 27%, HEX 면 38%·77%), TCP Server 수신 한계 64 KiB/s 는 460800 에서 여유 약 1.5배·921600 은 초과(가드 M21).

### 1.1 목표

- 3CH (공식 제품 아님. 제외).
- SSL/MQTT 채널 (4CH 에서 숨김 — 이 터미널은 평문 TCP/UDP/Serial 만).
- `refactored/` (개발 종료).
- NetTerm3 코드 이식 (WPF/C# 이라 불가). **개념만** 가져온다 (§3.3).
- 채널 간 데이터 교차오염을 **자동 판정**하는 기능은 이번 범위 밖 (§8 S7 후보, D9).

## 3. 핵심 설계

### 3.1 용어

| 용어 | 뜻 |
| --- | --- |
| **세션(Session)** | 터미널의 연결 하나. 지금의 `BaseProtocolTab` 인스턴스 하나와 같다 (프로토콜 + 수신창 + 송신창 + 핸들러) |
| **채널(Channel)** | **장치** 쪽 UART 채널 번호 CH1~CH4. 세션에 붙는 **선택적 라벨**(`session.channel = 1..4 \| None`) |

세션과 채널을 분리하는 이유: 한 채널을 이더넷 세션과 시리얼 세션 두 개로 볼 수도 있고(D2), 일반 장치(1채널)나 채널과 무관한 연결도 같은 터미널에서 쓰기 때문이다.

### 3.2 구조

```text
TerminalPanel (QWidget, Qt.Tool — 기존)
 ├─ 툴바: 전역 줄끝 · [＋ 세션▾] · [탭|그리드] · Export/Import · 📌 · ✕
 ├─ SessionManager                    ← 신규. 고정 4속성을 대체
 │    ├─ sessions: list[Session]      (생성 순서, 최대 MAX_SESSIONS)
 │    ├─ add(kind, **init) / remove(session)
 │    └─ 시그널: session_added · session_removed · state_changed(session)
 ├─ SessionContainer                  ← 신규. 같은 세션 위젯들을 두 방식으로 배치
 │    ├─ 탭 뷰  (QTabWidget — 기존 화면)
 │    └─ 그리드 뷰 (QGridLayout, 열 수 = ceil(sqrt(N)))
 ├─ SendBar (선택, S4)                ← 공용 송신: [입력] [대상 CH1 CH2 CH3 CH4 · All] [Send]
 └─ MacroPanel (공용 1개 — 기존)      ← 슬롯마다 target 필드만 추가

Session = BaseProtocolTab 하위 클래스(UDPTab · TCPClientTab · TCPServerTab · SerialTab) + 메타
          { key, name, channel, color }                 ← 얇은 메타만 추가
          각자 자기 ReceiveDisplay · SendWidget · 핸들러(QThread) 를 가진다 — 변경 없음
```

핵심은 `TerminalPanel` 이 4개 탭을 속성으로 쥐고 있는 방식(분석 §2.3 #1·#2)을 `SessionManager` 로 바꾸는 것이다. 세션 위젯과 핸들러 코드는 거의 그대로다.

### 3.3 NetTerm3 에서 가져올 것 / 가져오지 않을 것

| NetTerm3 요소 | 판단 | 이유 |
| --- | --- | --- |
| 세션 N개 + 탭/그리드 토글, 그리드 열 수 = ceil(sqrt(N)) | **가져온다** | 4채널 동시 표시의 검증된 형태 (분석 §1.4) |
| 세션 이름 변경(더블클릭), 헤더 상태 점, 헤더 드래그 순서 이동 | 가져온다 (순서 이동은 후순위) | 채널 식별 |
| 큐 상한 + 틱당 상한 + 드롭 카운트 + (배압) | **가져온다** (S6) | 4채널 부하 위험 (분석 §2.5(2)) |
| 수신 줄 조립 (`\n`, 120 ms 유휴, 512 B) | 가져온다 (S6, 옵션) | 채널 간 로그 비교 |
| 로그 실시간 파일 기록 | **가져온다** (S6 앞당기기 가능) | G3 |
| Save/Load Setup JSON | 가져온다 (S6) | 시험 환경 재현 |
| 시리얼 흐름제어 4종 / 시리얼 자동 재연결 | 가져온다 (S6, D12) | 4CH 채널별 흐름제어 시험 |
| HEX 전체 보기 | 가져온다 (S6, 옵션) | 바이너리 시험 |
| 명령줄 세션 생성 (`--tcp-client` 등) | 가져오지 않는다 | 이 앱은 GUI 가 주, 요구 없음 |
| **ANSI 해석 기본 켬** | **가져오지 않는다 (켜더라도 기본 끔)** | 켜면 수신 바이트가 변형되어 무결성 시험에 부적합 (분석 §1.8 a) |
| 채널 개념 없음 | **우리가 더한다** | 채널 번호 라벨 + 대상 지정 송신 |
| 시험 코드 없음 | **우리가 더한다** | §9 |

### 3.4 세션 모델 (제안 인터페이스)

```python
# terminal/session_manager.py (신규, 제안)
MAX_SESSIONS = 16           # 4채널 × (TCP Client + TCP Server + Serial) = 12 + 여유 (D10 권고, 사용자 결정 대기)

class SessionMeta:          # 위젯에 붙는 얇은 메타
    key: str                # "s1", "s2" … 설정 파일에서 대상 지정용, 이름이 바뀌어도 불변
    name: str               # 사용자 편집 가능. 기본 "TCP Client 1" / 장치 연동 시 "CH1 :5000"
    channel: int | None     # 1~4 또는 None
    color: str              # 채널 구분 색 (탭/그리드 헤더 표시)

class SessionManager(QObject):
    session_added = pyqtSignal(object)
    session_removed = pyqtSignal(object)
    state_changed = pyqtSignal(object, bool)      # session, connected
    def add(self, kind: str, **init) -> BaseProtocolTab: ...
    def remove(self, session) -> None: ...        # 핸들러 stop → wait 후 위젯 폐기
    def connected(self) -> list: ...
    def shutdown(self) -> None: ...               # 전 세션 stop() 먼저 일괄 → 그 다음 wait (병렬)
```

`BaseProtocolTab` 에 추가할 것은 `meta`, `snapshot()` / `restore(dict)` (설정 저장용), `set_compact(bool)` (그리드용) 정도다. 연결·송수신 코드는 건드리지 않는다.

## 5. 채널별 모델

### 5.1 연결

- 세션 추가: `[＋ 세션▾]` 메뉴 — UDP / TCP Client / TCP Server / Serial / **프리셋**(§5.6).
- 세션당 연결 설정·상태 표시는 지금 탭의 `Connection` 그룹 그대로.
- 같은 프로토콜 복수 허용. **서버 세션 둘이 같은 포트를 열면 OS 가 막지 않는다** — 둘 다 `listening` 으로 표시되고 접속은 먼저 연 쪽으로만 간다 [측정, 가드 문서 M1]. 핸들러가 `SO_REUSEADDR` 를 설정하기 때문이며(`comm_handlers.py:272`), 이 PC 에서 그 옵션을 빼도 직후 재listen 이 성공했다(M1c). 대책은 (1) `SessionGuard` P1 이 앱 안 중복을 막고 (2) 핸들러에서 `SO_REUSEADDR` 를 제거해 외부 프로세스 충돌(M1b)도 bind 오류로 드러나게 하는 것이다. UDP 같은 로컬 포트는 OS 가 10048 로 막는다(M2).
- **TCP Client + Server 동시 규칙 (`terminal_panel.py:214-222`)**: 이 규칙은 "불가"가 아니라 **둘 다 연결된 뒤 경고 팝업을 띄울 뿐**이다. 연결은 끊기지도 막히지도 않는다 [읽음, M10]. 4CH 는 채널마다 모드가 달라(예: CH1 서버 모드 ↔ 툴 클라이언트, CH2 클라이언트 모드 ↔ 툴 서버) 동시 사용이 정상 시나리오다. 규칙 해제는 팝업이 사라지는 것 하나뿐이다 (D5). 원래 사유는 여전히 [미확인]이나, 담당자 확인(2026-10-21)으로 NetTerm3 은 동시 사용이 되므로 해제에 장애가 없다는 근거는 확보됐다.
- 모든 공존 규칙(차단/경고/정보 48개)과 문구는 가드 문서 §2~§3.
- 세션 수 상한 `MAX_SESSIONS` (권고 16 — Mixed 채널 때문에 8 은 부족, D10).

### 5.2 송신

- 세션별 `SendWidget` 은 그대로 (Escape 해석, 줄끝, 주기 전송, 이력).
- **공용 송신바**(S4): 한 입력을 선택한 세션들로 동시에 보낸다. 대상: 채널 체크박스 + `All connected`. 줄끝은 세션별 설정을 따르되 "공용 줄끝 우선" 옵션 (현재의 `Per Tab` 콤보와 같은 개념, `terminal_panel.py:140-146`).
- 송신 직후 각 세션 수신창에 TX 로 기록 (`append_tx`, 현재 `_dispatch_send` 와 동일, `terminal_panel.py:209-212`). 단 현재는 **큐에 넣은 시점**에 TX 가 찍히고, 서버 세션에 클라이언트가 없거나 클라이언트 세션이 접속 전이어도 큐에 남았다가 나중에 전달된다 [측정, M4·M5]. 미연결 세션에 보내면 아무 표시 없이 무시된다 [읽음, M5b]. 송신 전 요약("CH1, CH3 → 2/4 송신 가능")과 이 동작의 정리는 가드 문서 §3 (S1~S8). **D13 확정(2026-10-21): 송신 가능 상태(UDP bound / TCP Client 접속됨 / TCP Server 클라이언트 접속됨 / Serial 열림)에서만 보내고, 그 외 전 상태는 폐기 + 이벤트 줄 `Send: not sent — {reason} ({n} B discarded)`, TX 줄은 핸들러가 소켓·시리얼에 넘긴 뒤 `sent(bytes)` 시그널로만 기록(전송 중 오류도 실패 이벤트), 큐 누적은 제거한다.** 불가 상태에서는 Send·공용 송신 대상이 비활성 + 툴팁이다. 상태별 현행/신규 동작은 가드 문서 §3.5 표, "연결되면 자동 송신"은 이번 범위 제외.

### 5.3 수신·표시

- 세션별 `ReceiveDisplay` 유지. 변경은 부하 보호뿐 (S6):
  - 대기 상한(`max_pending_bytes`)과 틱당 렌더 예산. 넘치면 **오래된 것을 버리고 `⚠ N B 생략` 한 줄을 표시**한다. 이때 파일 로그(§5.4)는 **수신 시점에 먼저 기록**되어 손실이 없다.
  - **4채널 합산 예산 검증(M21)**: 담당자 부하(4채널 동시 양방향 460800, 채널당 약 44,000 B/s)에서 4채널 RX 만 약 172 KiB/s, 양방향 표시면 약 344 KiB/s 다. 렌더 0.8 ms/KiB 기준 UI 시간은 약 14% / 27%, `hex` 모드(2.8배)는 약 38% / 77%. 예산·드롭 정책은 한 채널이 아니라 **4채널 합산 입력**으로 검증하고, 표시를 버려도 파일 로그는 무손실이어야 한다(가드 문서 §4.6, RR5·RR6).
  - 렌더 타이머: 지금은 수신창마다 50 ms `QTimer` (`receive_display.py:112-115`). 세션 N개면 N개의 타이머가 각자 깬다. **공용 타이머 하나가 라운드로빈으로 세션당 예산만큼 렌더**하는 구조가 UI 정지를 막는다. 수치(예산 크기)는 시작값일 뿐 실측으로 조정해야 한다 — 분석 §2.5(2): 0.7~0.9 ms/KiB (오프스크린 기준이라 실제 화면에서는 더 느릴 것으로 본다 [추정]).
- 옵션: 줄 조립, HEX 전체 보기 (NetTerm3 방식). 기본은 현재 표시(ASCII + 비ASCII `[HH]`)를 유지한다.
- ANSI 해석은 **넣더라도 기본 끔**이며, **HEX 와 ANSI 는 공존하지 않는다(D15 확정)** — 세션별 보기 모드 `text`(기본) / `hex` / `ansi` 중 하나만 고르고 하나를 켜면 다른 것은 자동으로 꺼진다. 상세 설계(원본 링버퍼 `RawHistory`, 청크 경계, HEX 형식, 배지, 비용 가중 예산)는 가드 문서 §4.
- 수치 보정: HEX 덤프 렌더는 현행 변환의 약 2.7~2.9배 비용이라 예산에 가중치가 필요하다 (M14). `max_lines=2000` 은 줄이 아니라 **틱 수**다 — `appendHtml` 한 번이 `<br>` 이 몇 개든 블록 1개 (M9). S6a 에서 표시 문자 수 기준으로 바로잡는다.


   `mode`: `active`(기본 = 현재 동작) · `all`(연결된 전부) · `select`(세션 key 목록). `target` 이 없는 구버전 JSON 은 `active` 로 읽는다 → **기존 저장값과 호환** (`set_all_data`, `macro_panel.py:413`).
3. `send_requested(bytes)` → `send_requested(bytes, target)`. 해석은 `TerminalPanel` 이 한다: 대상 세션 목록 → 각 `session.send_bytes(data)` (= 현재의 `handler.send` + `display.append_tx`).
4. 러너 스레드 → GUI 스레드로는 지금처럼 큐드 시그널을 쓴다. 여러 대상에 보내는 루프는 GUI 스레드에서 연속 호출(핸들러 `send` 는 deque 추가라 스레드 안전·즉시 반환) [읽음].
5. 대상이 연결 안 됨 / 사라짐: 그 대상은 건너뛰고 해당 세션 수신창에 이벤트 한 줄(`Macro: not connected, skipped`). 매크로 전체는 중단하지 않는다.
6. 행(row)마다 대상을 다르게 하는 안(`CH1: AT`, 지연, `CH2: AT`)은 더 유연하지만 표(Message/Delay)를 3열로 바꿔야 한다. 이번엔 슬롯 단위만, 행 단위는 후속 후보 (D6).

"동시" 송신의 한계: 핸들러가 50 ms 폴링이라 대상들에 닿는 시각이 어긋난다 — 루프백 측정에서 **4채널 편차 중앙 31 ms, 최대 32 ms**(핸들러 시작 시각이 제각각일 때), 맞추면 0.2 ms [측정]. 후속 프로토타입 2회 반복에서는 편차 중앙 31.2~46.5 ms(최대 48), 깨우기 적용 시 0.2 ms(최대 0.3) [측정, M7]. 송신 깨우기는 필수가 아니라 **사용자 옵션**(D19, §6.4, 기본 OFF)이다. 옵션이 꺼져 있는 동안은 사용자 안내문(가드 문서 §3.4 하단)에 오차를 명시한다.

### 5.6 장치 연동 (4CH 자동 구성)

현재 "Open in Terminal" 은 장치 프로파일의 **채널 0 키**(`OP LP BR DB PR SB LI`)만 써서 탭 4개를 채운다 (분석 §2.3 #5). 4CH 는 채널 0~3 이 각자 값을 갖는다: 채널 0 은 레거시 코드, 채널 1~3 은 `channel_field_map.CH_FIELD_MAP` (`channel_field_map.py:31-57`)의 코드 (`AO/TO/JO` 동작 모드, `QL/GL/CL` 로컬 포트, `QH/GH/CH` 원격 IP, `AP/TP/JP` 원격 포트, `EB/WB/YB` 보레이트 …).

제안: 순수 함수 하나를 신설한다 (Qt 무관 → 시험하기 쉽다).

```python
# terminal/device_endpoints.py (신규, 제안)
def endpoints_from_profile(profile: dict, spec) -> list[ChannelEndpoint]:
    """장치 프로파일 + spec(channels 수) → 채널별 {channel, op_mode, ip, local_port,
    remote_ip, remote_port, baud, databit, parity, stopbit, flow}"""
```

세션 구성 규칙 (**D8 확정** — 4CH 담당자 2026-10-21):

| 장치 채널 동작(OP) | 툴 세션 | 주소/포트 | 비고 |
| --- | --- | --- | --- |
| 0 TCP Client | **TCP Server** (리슨) | 포트 = 장치 채널의 **원격 포트(RP)** | **확정.** 현재 `fill_from_device` 가 모든 탭에 같은 LP 를 넣는 것은 틀림(분석 §2.7) → TASKS `TODO-TERM-OPEN-IN-TERMINAL-PORT` |
| 1 TCP Server | **TCP Client** | 장치 IP : 채널 **로컬 포트(LP)** | 현재 코드와 같은 방향. 장치 서버 모드는 접속 1개이고 두 번째는 장치가 거부(기존 유지) |
| 2 Mixed | **TCP Client (장치 IP : LP) + TCP Server (리슨 RP) 둘 다** | 기본은 장치가 서버로 동작. 클라이언트가 붙기 전에 시리얼 데이터가 들어오면 장치가 클라이언트 모드로 전환 → 한 채널에 툴 Client+Server 세션이 모두 필요할 수 있다 | **확정.** 같은 채널 Client+Server 쌍은 경고 금지(가드 L3). D5 해제의 필수 근거 |
| 3 UDP | UDP | **툴 로컬 포트 = 장치 원격 포트, 툴 원격 포트 = 장치 로컬 포트**, 원격 IP = 장치 IP | **확정.** UDP 방향성 문서 `research/2026-04-27-udp-remote-local-port-explained.md` 는 읽지 않았다 |
| 4~6 (SSL/MQTT) | — | — | 4CH 에서 숨김. 무시 |

시리얼 쪽: 채널별 UART 파라미터(보레이트·데이터·패리티·정지·흐름)로 Serial 세션의 설정을 채울 수 있다. **COM 포트 번호는 PC 에서 장치의 어느 UART 와 이어졌는지 알 수 없으므로 자동 선택 불가** → 사용자가 고른다 (사람이 확인).

프리셋(메뉴): `4CH 이더넷` (TCP Client 4개를 CH1~4 로 라벨) / `4CH 이더넷+시리얼` (D2 결과에 따라) / **`Mixed 채널`**(채널 n 에 TCP Client(장치 IP:LP) + TCP Server(리슨 RP) + 시리얼(COM 은 사용자가 선택) 세 세션을 한 번에 만든다 — 검토 후보) / `Classic` (현재의 4탭).

## 6. 스레드·이벤트 구조

### 6.1 현행 유지 + 변경점

```text
   [ 세션 1 ]        [ 세션 2 ]  …  [ 세션 N ]               각 세션 = 독립
 핸들러(QThread)   핸들러(QThread)   핸들러(QThread)         select 폴링 루프 (변경 없음, §6.4 선택)
   │ data_received    │                 │                    스레드 → GUI: 시그널(큐드)
   ▼                  ▼                 ▼
 ReceiveDisplay    ReceiveDisplay   ReceiveDisplay           deque 적재 (상한 추가, S6)
   └────────────┬────────────┴───────────┘
        공용 렌더 타이머(S6)  ──▶ 세션당 예산만큼 렌더
 MacroRunner(QThread) ──send_requested(bytes, target)──▶ TerminalPanel(GUI) ──▶ 대상 세션들의 send()
```

- 핸들러는 변경하지 않는다. 스레드 수 = 세션 수(최대 16) + 매크로 러너 1 — 문제 되는 규모는 아니다 [추정].
- 새 스레드는 만들지 않는다.

### 6.2 수명 규칙 (전례: 커밋 `658f2f8` QThread GC 크래시)

1. 핸들러의 소유자는 세션이다. 세션이 폐기되기 전에 `stop()` → `wait()` 로 스레드를 끝낸 뒤에만 참조를 놓는다.
2. `SessionManager.remove()` 와 `shutdown()` 은 **먼저 모든 핸들러에 `stop()` 을 일괄 호출한 다음** 한꺼번에 `wait()` 한다 (현재는 탭별 순차 `wait(2000)`, 분석 §2.3 #8). 4채널 종료 지연이 2초×4 → 약 2초로 줄어든다 [추정].
3. 핸들러 시그널의 람다 연결(`lambda e: self.display...`, `protocol_tabs.py:302,386,474,617`)이 세션 폐기 후 호출되지 않도록 폐기 시 `disconnect` 한다 (시험으로 확인).

### 6.3 UI 스레드 예산

분석 §2.5(2) 측정에 따라 수신창 렌더는 양에 비례(≈0.8 ms/KiB)하고 상한이 없다. 공용 타이머가 틱마다 세션당 렌더 바이트 예산을 두고(시작값 예: 세션당 8 KiB ≈ 7 ms), 못 그린 분은 다음 틱으로 넘기며, 대기량이 상한(예: 세션당 1 MiB)을 넘으면 오래된 쪽을 버리고 표시한다. **수치는 시작값이며 실기기 4채널 고속 시험으로 조정한다** (사람 확인).

### 6.4 송신 깨우기 — 사용자 옵션 `Fast send wake` (D19 확정, 기본 OFF)

**배경과 측정 (M7)**: 핸들러 루프는 송신 큐를 비운 뒤 `select(..., 0.05)` 에서 잔다(`comm_handlers.py:100-112,184-197`). 그 사이 들어온 송신은 최대 50 ms 대기한다 — 루프백 `send()`→수신 중앙 25~29 ms, p90 56 ms, 최대 약 64 ms [측정]. `socketpair` 깨우기 프로토타입(저장소 미수정, 2회 반복)은 4채널 동시 송신에서 지연 중앙 24.9~29.6 ms(최대 63) → 0.3 ms(최대 0.6), 편차 중앙 31.2~46.5 ms(최대 48) → 0.2 ms(최대 0.3) [측정, M7]. **TCP Client 핸들러만 측정했고 UDP·Server 는 미측정**이며, 담당자가 4채널 동시 송신/수신 편차 시험을 해 본 적이 없어 필수 근거가 약하다. 그래서 사용자 결정으로 **옵션**이다.

**옵션 설계**

| 항목 | 설계 |
| --- | --- |
| UI 이름 | `Fast send wake` (설정 대화의 체크박스) |
| 전역 기본값 | `settings.tx_wake_default`, 출하 값 **false**(현행 50 ms 폴링). 새 세션은 이 값으로 시작 |
| 세션별 override | 기술적으로 쉽다(핸들러 생성 인자 1개). 그러나 세션마다 지연 특성이 달라지면 "동시 송신" 비교 시험을 오염시키고 UI 도 복잡해진다. **권고: 1차는 전역만, JSON 스키마에 세션별 `tx_wake: null`(= 전역을 따름)을 예약**하고 UI 는 노출하지 않는다 [검토 결과, 사용자 확인 가능] |
| 적용 시점 | 연결(핸들러 생성) 시 읽는다. 연결 중 토글은 **다음 연결부터** 적용(핫스왑 없음) — 도움말에 명시 |
| 저장 | `terminal_config.json` v2 `settings.tx_wake_default`, 세션 항목의 `tx_wake`(기본 null). QSettings 자동 복원 키 `terminal/tx_wake_default` |
| 구현 | 핸들러 생성자에 `tx_wake: bool = False`. ON 이면 `socketpair` 를 만들어 읽기 쪽을 `select` 목록에 넣고 `send()` 가 쓰기 쪽에 1바이트를 쓴다. OFF 면 wake 소켓을 만들지 않고 현행 경로 그대로. Serial 은 `msleep(10)` 이라 대상 아님(`comm_handlers.py:464`). Windows `socketpair` 는 Python 3.5+ [일반지식], 프로토타입이 이 PC 에서 동작했다 |
| 안내문 | 가드 §3.4 의 "동시 송신" 안내문이 옵션 현재 값으로 문구를 고른다 |

**OFF → ON 으로 기본값을 바꿀 조건 (모두 충족, 사용자 승인 필요)**

1. UDP·TCP Server·TCP Client 핸들러 각각 루프백 2회 반복 측정에서 지연 중앙 < 1 ms, 4채널 편차 중앙 < 1 ms (UDP·Server 는 아직 미측정 — 가드 TW2 가 첫 측정).
2. 회귀 없음: 유휴 CPU 사용률, `stop()`→`wait()` 시간(시작값 ≤ 2 s), wake 소켓 정리(TW3).
3. 실기기 4CH 에서 4채널 동시 송신 1회 확인(가드 H18).
4. 서버 수신 구조 수정(M8)과 함께 들어가 서버 핸들러의 `select` 대상 변경이 검증됨.

**UI 도움말 문구** (D16: 영어 확정안; 한국어는 의미 명세)

- English: "Fast send wake: wakes the I/O thread as soon as you press Send, instead of waiting for its next 50 ms poll. Measured on loopback with TCP Client sessions only: send delay 25–30 ms → 0.3 ms, spread across 4 channels 31–46 ms → 0.2 ms. UDP and TCP Server sessions have not been measured yet. Applies from the next connection. Default: off."
- 한국어 명세: 송신 버튼을 누르는 즉시 I/O 스레드를 깨워, 다음 50 ms 폴링을 기다리지 않는다. 루프백에서 TCP Client 세션만 측정: 송신 지연 25~30 ms → 0.3 ms, 4채널 편차 31~46 ms → 0.2 ms. UDP·TCP Server 는 아직 측정하지 않았다. 다음 연결부터 적용. 기본값 꺼짐.

**시험**: 옵션 on/off 양쪽(가드 문서 §5.3.2 TW1~TW5). 프로토타입 `tx_wake_proto.py` 를 시험으로 승격한다.

## 8. 단계 계획

각 단계는 **로컬 커밋**으로 끝나며 push/PR 은 하지 않는다 (팀장 승인 전 원칙). 되돌림은 해당 커밋 revert. 규모는 상대 크기(S/M/L)일 뿐 시간 약속이 아니다.
