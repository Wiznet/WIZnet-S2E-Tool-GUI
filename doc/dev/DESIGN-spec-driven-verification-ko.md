# 스펙 주도 자동 검증 — 전체 설계

> 상태: **설계안 (구현 전, 승인 대기)**. 이 문서에 동의가 나기 전에는 코드를 바꾸지 않는다.
> 표기: **[확인]** 코드·git·실행으로 확인 / **[추정]** 근거는 있으나 검증 안 함 / **[미확인]** 모름. 처음 쓴 날: 2026-10-19.
> 배경: 4CH 담당자 답변(`(내부 작업 문서)/research/2026-10-19-w55rp20-4ch-fw-limits.md`)에서 "펌웨어 브랜치마다 응답·저장 길이 검사 유무가 다르다"는 것이 드러났고, 그에 대한 대응이 (1) 길이 검사를 스펙에서 자동으로 (2) 사람이 목록에서 선택하면 자동 시험이 도는 검증 모드, 두 요구로 정리됐다.

---

## 0. 한 장 요약

| 질문 | 답 |
| --- | --- |
| 무엇을 만드나 | ① **스펙 분석기**(장치 없이 스펙만으로 길이·응답 크기·누락을 계산) ② 그 결과를 쓰는 **자동 적용**(입력칸 길이, 조회 분할) ③ **검증 모드**(검색 후 선택한 장치를 자동으로 점검하고 보고서 작성) |
| 핵심 원칙 | **코드가 확인해도 충분한 것은 코드가, 사실의 출처가 사람/펌웨어인 것은 사람이 확인한다.** 코드는 사람이 확인해야 할 것을 **후보 목록으로 뽑아 주기만** 한다 |
| 가장 중요한 경계 | 스펙의 숫자(길이·버퍼·검사 유무)가 **실제 펌웨어와 같은지**는 코드로 알 수 없다. 스펙은 우리가 쓴 거울이다 |
| 장치를 바꾸는가 | 단계별로 다르다. L0(읽기)는 변경 없음. L1(왕복)·L2(경계)는 **사람 승인 + 자동 원복 + 백업** 전제 |
| 단계 | A 스펙 분석(장치 무관) → B 읽기 감사 + 보고서 → C 왕복 → D 경계값. **각 단계 끝에 사용자 확인 게이트** |
| 시작 조건 | §9 의 **결정 항목 D1~D9 중 최소 D1~D4 확정** |

## 1. 현재 상태 — 이미 있는 것과 없는 것

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| Apply 때 스펙으로 값 검증 | **있음** (모든 명령, 스펙에 정의된 것은) | `main_gui.py:6209 _is_valid_setcmd_param` → `CmdEntry.is_valid` |
| 입력칸 길이 제한(`maxLength`) | **3개 위젯만 수동 매핑** (NP/PI/PP) | `_TEXT_LIMIT_WIDGETS` (이번 작업) |
| 명령 → 위젯 연결 | **스펙에 없음**. 스펙의 `ui.widget` 은 위젯 *종류*(`label`/`lineedit`)이고 객체 이름(`connect_pw` 등)은 `main_gui.py` 에 흩어져 있다 | `specs/commands/*.yaml`, `main_gui.py` |
| 응답 크기 검사 | 응답이 **버퍼에 닿은 뒤** 경고(`[SIZE]`), 버퍼 크기를 아는 기종만 | `WIZMSGHandler._warn_if_reply_reaches_buffer` |
| 조회 분할 | **WIZ752SR-12x 만** 손으로 만든 3분할 | `cmd_2p_search_chunks`, `search_chunks()` |
| 스펙 스키마 | device `fw_constraints` 는 **확장 가능**(`additionalProperties: true`). **명령 항목은 확장 불가**(`additionalProperties: false`) → 명령에 새 키를 넣으려면 스키마·로더(`CmdEntry`)를 바꿔야 한다 | `specs/schema/*.json`, `device_spec_loader.py` |
| 장치 모사 | 가짜 장치가 **버퍼 크기, 초과 시 덮어쓰기 기록, 절단 모드(`truncate_reply`), 도메인 칸 크기, 거부 시 SV 스킵(`abort_on_error`), 재부팅 시간** 을 흉내 낸다 | `tests/fake_segcp_device.py` `FirmwareQuirks` |
| 스펙에서 최대 폭 계산 | **가능함을 확인.** 정규식 파서로 4CH 조회 143개 중 114개(2CH 89개 중 68개)의 최대 폭이 자동으로 나온다. 나머지는 정규식이 비어 있거나(`MN/VR/ST/UN/SP/QU/QP/QC/PU` …) lookahead(`RH`) 라 못 읽는다 | 임시 계산(2026-10-19) |
| 응답에 빠진 명령 감지 | **없음** | — |
| 자동 검증 모드 | **없음** | — |

## 2. 무엇이 "코드가 확인하면 충분"하고 무엇이 "사람이 확인해야 하는가"

이 문서의 핵심 구분이다. 기준은 하나: **판정의 근거가 우리 저장소 안에 있는가.**

### 2-1. 코드가 확인해도 충분한 것 (자동, 사람 검토 불필요)

| ID | 확인 내용 | 근거가 저장소 안에 있는 이유 |
| --- | --- | --- |
| C-1 | 스펙이 스키마를 지키는가, 정규식이 컴파일되는가, `values` 키가 정규식과 모순 없는가 | 스펙 파일 자체가 판정 대상 |
| C-2 | 명령 코드 충돌, 그룹 중복 정의 | 이미 `validate_schemas.py` 가 한다 |
| C-3 | 스펙에서 계산한 **최대 폭**이 존재하는 명령 목록, **폭을 알 수 없는 명령 목록** | 스펙만 읽으면 계산됨 (§1) |
| C-4 | 장치별 **최악 응답 크기 계산**과 `config_buf_size` 대비 비율(스펙 값을 *진실로 가정*한 계산) | 스펙 + 조회 목록 |
| C-5 | 입력칸 `maxLength` 가 스펙 폭과 같은가, 위젯이 연결되지 않은 쓰기 가능 명령이 있는가 | 위젯 표 + 스펙 |
| C-6 | 한 요청(조회 청크)의 **최악 응답이 예산 이하**가 되는 분할 계획 | 계산 |
| C-7 | 받은 응답에서 **조회한 명령이 빠졌는가**(절단 후보), **스펙을 위반하는 값**이 왔는가, **응답 크기**가 얼마인가 | 요청과 응답이 모두 툴 안에 있음 |
| C-8 | **왕복 일치**: 쓴 값 == 다시 읽은 값, **원복 일치**: 시험 후 값 == 시험 전 값 | 두 번의 읽기 비교 |
| C-9 | **툴 측 거부**: 허용 범위 밖 값이 `is_valid` 에서 막히는가(장치로 보내지 않음) | 순수 함수 |
| C-10 | 병합·표시 일관성: 평행 배열 길이, MAC 중복(정규화 키), 주황 행 잔존 | 툴 내부 상태 |
| C-11 | 위 모두를 **가짜 장치**(버퍼·절단·덮어쓰기 모사)에 돌려 **검증기 자신이 맞게 동작**하는지 | 시뮬레이터가 저장소에 있음 |

### 2-2. 사람이 반드시 확인해야 하는 것 (코드로는 판정 불가)

| ID | 확인 내용 | 사람이어야 하는 이유 | 확인할 사람 | 증거 형태 |
| --- | --- | --- | --- | --- |
| H-1 | **펌웨어 한도의 진실**: `config_buf_size`, 응답 절단 유무, **저장 길이 검사 유무**(`length_checked`), 칸별 실제 최대 길이 | 스펙은 우리가 옮겨 적은 값이다. 코드는 그 값을 *가정*할 뿐 실제 펌웨어와 대조하지 못한다 | 제품 펌웨어 담당자 | 펌웨어 커밋 해시 + 담당자 확인 일시를 스펙 주석에 남김 |
| H-2 | **위험 분류(`risk`)**: 어떤 명령을 바꾸면 접속이 끊기거나(IP·IM) 접근이 막히거나(NP) 장치 동작이 바뀌는가(OP·BR) | 장치 동작의 의미는 코드에 없다 | 제품 담당자 | 분류표에 서명(일시·이름) |
| H-3 | **길이 정보가 없는 명령의 실제 최대 길이**(`MN`, `VR`, MQTT 문자열 등) | C-3 이 후보를 뽑지만 값은 펌웨어 소스에만 있다 | 펌웨어 담당자 | 소스 위치 |
| H-4 | **모델 대 실측 편차의 해석**: 계산 응답 크기와 실제 응답 크기가 다를 때 어느 쪽이 틀렸는가 | 코드는 차이를 보고만 한다 | 시험 담당자 | 실기기 보고서 |
| H-5 | **L1·L2 실행 승인과 대상 장치 지정**(어떤 실장치에 쓰기를 허용하는가) | 되돌리기 어려운 동작, 장치 소유자만 알 수 있음 | 시험 담당자 + 팀장 | 실행 전 확인 대화상자 + 로그 |
| H-6 | **결함 판정**: 검증 보고서의 FAIL 이 툴 결함인지, 펌웨어 결함인지, 스펙 오류인지 | 원인 귀속은 맥락이 필요 | 개발자 | 이슈 등록 |
| H-7 | **제품 범위**: 어떤 장치를 공식 제품으로 보고 검증 대상에 넣는가(3CH 사례) | 비즈니스 결정 | 팀장 | 스펙 머리말 기록 |
| H-8 | **릴리즈·배포 결정**(검증 모드를 고객 빌드에 노출할지, 노출 수준) | 외부 영향 | 팀장 | 승인 |
| H-9 | **실장치 최초 1회 대조**: 새 검증기가 실제 장치에서 가짜 장치와 같은 결론을 내는지 | 가짜 장치는 거울이다 | 시험 담당자 | 보고서 비교 |

### 2-3. 혼합 — 코드가 후보를 만들고 사람이 확정

| ID | 코드의 역할 | 사람의 역할 |
| --- | --- | --- |
| M-1 | "길이 정보 없음" 목록 생성(C-3) | H-3 으로 값을 채워 스펙에 반영 |
| M-2 | `risk` 초안 제안(스펙의 `ui.group` — `ip_mode`, `conn_password`, `device_info` — 에서 자동 추정) | H-2 로 확정. **미확정 명령은 L1 에서 제외(기본값 = 위험)** |
| M-3 | 절단 의심(명령 누락) 경고 | H-6 로 원인 판단 |

> **규칙**: 코드가 "안전하다"고 단정해야 하는 자리에 사람의 확정 정보가 비어 있으면 **위험한 쪽을 기본값**으로 한다(미분류 명령은 변경 금지, `length_checked` 미기재 장치는 길이 시험 금지).

## 3. 아키텍처

```
specs/*.yaml ──► device_spec_loader ──► DeviceSpec
                                           │
              ┌────────────────────────────┤
              ▼                            ▼
       spec_analysis.py  (순수 함수, 장치 무관)        widget_map.py (명령→위젯 단일 표)
        · max_width(entry)                              · 위젯 maxLength 자동 적용
        · worst_case_reply_size(spec, cmds)             · 미연결 쓰기 명령 감지
        · plan_chunks(spec, budget)
        · audit_spec(spec) → findings
              │
              ├──► WIZMakeCMD.search_chunks (자동 분할, 장치별 opt-in)
              ├──► tests/ (스펙 감사 시험 — CI)
              └──► verify/ (검증 모드)
                     checks.py   : 응답/상태 점검(순수 함수, C-7~C-10)
                     runner.py   : QThread 워커, 레벨별 실행, 백업/원복
                     report.py   : 마크다운/CSV 보고서
                     ui_entry    : 메뉴 진입점(기본 숨김)
```

### 3-1. 스펙 확장 (사람이 채우는 정보가 들어가는 자리)

| 위치 | 필드 | 의미 | 채우는 사람 | 기본값(비었을 때) |
| --- | --- | --- | --- | --- |
| device `fw_constraints` | `config_buf_size` | 응답 버퍼 B | 펌웨어 담당자(H-1) | 0 = 모름 → 크기 판정 안 함 |
| device `fw_constraints` | `reply_truncation` | 버퍼 남은 양이 `reply_truncation_min_free` 미만이면 응답을 자른다 | H-1 | false |
| device `fw_constraints` | `reply_truncation_min_free` | 위 임계(4CH 256) | H-1 | 0 |
| device `fw_constraints` | `length_checked` | 펌웨어가 저장 길이를 검사해 거부하는가 | H-1 | **false (=검사 없음으로 간주)** |
| device `fw_constraints` | `sources` | 위 값의 출처(펌웨어 커밋, 확인자, 일시) | 작성자 | 비면 감사 경고 |
| command | `max_len` | 정규식으로 못 읽는 문자열 칸의 최대 길이 | H-3 | 비면 "폭 미상" |
| command | `risk` | `safe` / `network` / `access` / `disruptive` | H-2 | **미분류 = 변경 금지** |

> 명령 쪽은 스키마가 `additionalProperties: false` 라 **스키마 + 로더(`CmdEntry`) + 시험을 함께** 바꿔야 한다. device 쪽은 확장 가능하지만 `FWConfig` dataclass 필드는 추가해야 한다.
> 정규식 폭 계산은 `re._parser`(비공개 API)를 쓴다. **파이썬 버전이 바뀌면 깨질 수 있어** 래퍼 + 고정 시험으로 감싼다 [확인: 프로젝트 파이썬 3.12 고정 — §10].

### 3-2. 길이 검사 자동화 (요구 1)

| 층 | 방법 | 사람 확인 |
| --- | --- | --- |
| 전송 단계(Apply) | **이미 자동** — 스펙을 채우면 끝 | 스펙 값의 근거(H-1, H-3) |
| 입력 단계(UI) | `widget_map` 의 (명령 → 위젯) 표에서 스펙 최대 폭을 `maxLength` 로 | 표가 완전한지는 **코드가 감사**(C-5), 표 최초 작성만 사람이 한 번 검토 |
| 조회 분할 | `plan_chunks()` 가 최악 응답이 예산(예: `min(버퍼 − 임계, UDP 1472)`) 이하가 되게 분할. **장치별 opt-in**(스펙 `search_chunking: auto`). 752 의 기존 3분할 표는 그대로 | 예산식과 opt-in 대상 결정(D3) |
| 스펙 누락 | `audit_spec()` 가 폭 미상 명령, 출처 없는 한도, 미분류 `risk` 를 목록으로 | 목록의 항목을 채움(M-1, M-2) |

## 4. 검증 모드 (요구 2)

### 4-1. 사용 흐름
1. 평소처럼 **Device Search** → 목록에서 대상 장치를 하나 이상 **선택**(체크).
2. **Tools → Verify selected devices…**(기본 숨김) → 레벨 선택 → 확인 대화상자(L1 이상은 *장치 이름·MAC·변경될 명령 수·원복 방법* 표시).
3. 장치마다 **순차** 실행(한 대씩). 진행 막대, **중지 버튼**.
4. 끝나면 **보고서**(마크다운/CSV)를 저장하고 폴더를 연다. 같은 보고서가 진단 zip(`TODO-DIAG-REPORT`)의 본문이 된다.

### 4-2. 레벨

| 레벨 | 동작 | 장치 변경 | 코드 확인 | 사람 확인 |
| --- | --- | --- | --- | --- |
| **L0 읽기 감사** | 조회(분할 포함) 후 C-7: 명령 누락, 스펙 위반 값, 응답 크기, 예상 밖 명령, Phase 1 대 Phase 3 불일치, MAC 중복(C-10) | 없음 | 전부 | 결과 해석(H-4, H-6) |
| **L1 왕복** | `risk = safe` 로 **확정된 명령만** 값을 바꾸고 재조회로 확인(C-8) → **자동 원복** | 있음(원복) | 값 일치, 원복 일치 | **실행 승인(H-5)**, `risk` 분류(H-2) |
| **L2 경계값** | 허용 최대/최소를 보내 유지 확인. 허용 범위 **밖** 값은 *보내지 않고* `is_valid` 로만 확인(C-9) | 있음 | 유지·거부 | **`length_checked=true` 로 확인된 장치만**(H-1), 승인(H-5) |

### 4-3. 안전장치 (L1·L2 필수)
1. **백업 선행**: 시작 전 전체 프로파일을 파일로 저장(이 파일 없이는 시작하지 않는다).
2. **원복 보장**: 정상·예외·중지 어떤 경로든 마지막에 원복을 시도하고, 원복 후 재조회로 **원래 값과 같은지 확인**(C-8). 같지 않으면 큰 경고와 백업 파일 경로를 표시.
3. **대상 제한**: BOOT/UPGRADE 상태, `risk` 미분류 명령, `length_checked` 미기재 장치의 길이 시험은 **자동 제외**(기본 = 위험).
4. **순차·1대씩**, 장치 응답이 없으면 그 장치는 중단하고 다음 장치로(원복 못 한 상태를 보고서 맨 위에).
5. **한 요청에 한 필드**: 거부 시 `abort_on_error` 때문에 같은 요청의 저장이 통째로 취소되는 펌웨어가 있으므로, 시험은 필드를 섞지 않는다.
6. **실장치 첫 실행은 L0 만**(H-9). 가짜 장치 결과와 비교해 일치한 뒤 L1 허용.
7. 노출: 기본 숨김(Option → Advanced 에서 활성화 또는 실행 인자). **고객 빌드에는 L0 만 노출하는 안**(D8).

### 4-4. 가짜 장치 연동 (코드 확인의 핵심 수단)
- 같은 검사 코드를 `tests/fake_fleet` 에 돌려 **스펙을 고칠 때마다 CI 로 자동 회귀**.
- 가짜 장치의 `FirmwareQuirks` 로 "버퍼 초과 → 덮어쓰기 기록", "절단", "저장 거부 시 SV 스킵"을 재현하므로 **검증기가 이 상황들을 올바르게 감지하는지**를 시험한다(C-11).
- ⚠ 가짜 장치는 **스펙을 되비추는 거울**이다(원칙, `fake_segcp_device.py` 머리말). 스펙이 실펌웨어와 다르면 같이 틀린다 → H-1, H-9 가 필요한 이유.

### 4-5. 보고서(출력)
- 머리: 툴 버전, 장치(MAC·제품·FW), 레벨, 시작·종료, **원복 상태(성공/실패/미수행)**.
- 본문 표: 명령별 `[읽기 값 | 스펙 판정 | 응답 존재 | (L1) 쓴 값/읽은 값/원복 | 비고]`, 응답 크기와 버퍼 비율, 누락 명령 목록, 스펙 감사 경고.
- 끝: **사람이 확인해야 할 항목 목록**(§2-2 의 해당 ID 를 자동으로 나열 — 예: "폭 미상 명령 29개: H-3 필요", "risk 미분류 12개: L1 제외").

## 10. 이 설계가 확인하지 못한 것 (구현 전 점검 대상)
- 정규식 폭 계산의 비공개 API(`re._parser`) 의존: 프로젝트 파이썬은 `.python-version` 로 **3.12(실행 3.12.4)** 고정이고 `re._parser` 가 동작함을 확인했다 [확인]. 버전을 올릴 때만 재검증하면 되며, 래퍼 + 고정 시험으로 감싼다.
- 명령 → 위젯 표를 만들 때 위젯이 몇 개인지(수작업 규모) [미확인] — A2 시작 시 먼저 센다.
- L1 안전 필드가 실제로 몇 개 남는지 — `risk` 분류 후에야 안다 [미확인].
- 조회 분할이 검색 시간에 미치는 영향 — 측정 필요 [미확인].
- SET 확인 쿼리(`setcommand` 의 GET 꼬리)와 `_get_expected_min_resp_len` 이 분할과 맞물리는 방식 — A2 설계 때 따로 점검 [미확인].
